# 灵枢悬赏板 · 规则（v0.1）

> 一句话：把本仓的 issue 池变成**可认领的悬赏任务**——外部人或 AI agent 认领 → 交付 →
> 过**验收四闸** → 记入**可追溯的声誉账本**。
> **不涉资金**：结算是声誉制（可查、可降、可追溯），不是钱。

设计稿：[悬赏板设计 v0.1](../spec/悬赏板设计_v0.1.md)（2026-10-09）。
机械件：workflow [`.github/workflows/bounty.yml`](../../.github/workflows/bounty.yml)（薄壳·只做事件路由）／
状态机 [`scripts/bounty_board.py`](../../scripts/bounty_board.py)（可本地跑·可离线演练·可测）／
发布模板 [`.github/ISSUE_TEMPLATE/bounty.yml`](../../.github/ISSUE_TEMPLATE/bounty.yml)。
账本 [`ledger.json`](ledger.json) ｜ 荣誉榜 [`board.md`](board.md)。
悬赏清单 [`悬赏清单.md`](悬赏清单.md)（**统一查看面**：真源 [`悬赏.json`](悬赏.json) → 生成器 [`scripts/bounty_list.py`](../../scripts/bounty_list.py)）／ 守卫 [`tests/test_bounty_list.py`](../../tests/test_bounty_list.py)。

## 〇、为什么这些方向优先（价值论证）

> **本站不宣布优先级，只给可核验的事实**——每条数据附来源 URL，可自行核验。完整论证见
> [价值论证 v0.1](../spec/价值论证_v0.1.md)。

### 行业锚

| 事实 | 数值 | 来源 |
|---|---|---|
| **Mem0** 融资 | **USD 24M** | Entrepreneur India · 2025-10-29 |
| **红熊 AI**（境内） | 8000 万元 Pre-A+ 轮，**公司估值 7.5 亿元** | 36氪 |
| 生成式 AI 在企业知识管理与搜索市场 | 2026 年约 **USD 8.81B** → 2031 年 **USD 27.43B**（**CAGR 28.56%**） | Mordor Intelligence |

**读法**：记忆层**不是某个产品的功能，而是一个被资本单独定价的赛道**——境内外都有独立记忆公司拿到千万到亿美元级融资，境内头部估值达数亿元量级。

### 为什么记忆系统优先

1. **记忆是所有能力的前置**——检索、推理、协作、信任都建立在「记得住、找得到、改得对」之上。**本站活证据**：**#7** 
   `verify(falsified)` 绕过删除闸 ⇒ 一次调用**永久删掉一条记忆**、`restore()` 找不回；**#9** 审核接受后有效期丢失 ⇒ **过期记忆仍被召回**。
2. **行业用资本投票**——见上表。
3. **本站已有可复跑的实测收益**——#2 证据保留 **17.6 → 29.6**、#8 hit@10 **0.076 → 1.00**、#5 625 题 **0.979**。

### 为什么理论与算法「资源不限」

1. **算法是乘数，不是加数**——一份算法改进被**所有下游复用**，边际成本 ≈ 0、边际收益 = 全站。
2. **瓶颈在算法层，不在工程层**——**#3** 发现**判分链自身**有 3 处缺陷：**量具错了，所有评测结论都错**；工程手段发现不了「量具不可信」。
3. **理论结论可独立复算**——零 LLM 判官、定点变异自证 ⇒ 可信上限高、验证成本低。

**边界**：站内**不固化权重**（[价值评价规格 v0.1](../spec/价值评价规格_v0.1.md) V4）——以上是**公开常识的引用**，优先级仍由使用者按自己的资金与权重判断。

## 一、状态机（六态 · 映射 GitHub labels）

```
bounty:open ──/claim──▶ bounty:claimed ──/deliver──▶ bounty:delivered ──验收──▶ bounty:verified ──▶ bounty:settled
                              │                                                    │
                              └── 72h 超时未交付 ──▶ 回板 bounty:open               └── 争议 ──▶ bounty:disputed
```

- **入选标记**：`bounty`（维护者打——打了才算悬赏任务）。
- **难度标签**：`difficulty:{easy|medium|hard|expert}`（决定结算分，见 §四）。
- **态标签**：`bounty:{open|claimed|delivered|verified|settled|expired|disputed}`。
- 权威记录不是标签，而是**评论里的机器标记**（`<!-- bounty:v1 {…} -->`）：标签是人眼视图，
  标记是账（持有者、到期时间、轮次都在里面）。两者不一致时以标记为准。
- **`bounty:expired` 在 v0.1 不驻留**：超时那一刻直接回板 `bounty:open`，只把
  「超时」这条事件与评论留在痕里（`expired` 仍属可认领态，以便外部工具识别该窗口）。

## 二、命令面（MVP 只做 GitHub 评论命令）

**只认「命令在最前、行首」的词**：`/claim` 必须是评论首个非空行的第一个词。
正文中间的 `/claim`（例如「我觉得应该 /claim 一下」）**不是命令**，机器人不响应。

| 命令 | 谁用 | 校验（未过即回评说明原因） | 效果 |
|---|---|---|---|
| `/claim` | 任何人 | ① 无当前持有者 ② `bounty` 标签在且在 `open`/`expired` 态 ③ 本人并发认领数 ≤ **2** | 上锁 + 记到期时间（**72h**） |
| `/deliver <PR 链接或证据块>` | 认领者 | ① 仅认领人可交付 ② 必带链接或证据块 ③ 轮次 ≤ **3** | 转 `bounty:delivered`，等验收 |
| `/withdraw` | 认领者 | 仅认领人可释放 | 主动释放，任务回板；**不影响声誉** |
| `/dispute <理由>` | 双方（认领者／维护者／issue 作者） | 必带理由 | 转 `bounty:disputed`，维护者仲裁并留痕 |
| `/verify [pass\|fail] <理由>` | 维护者 | 态为 `delivered` | 通过 ⇒ `bounty:verified`；不通过 ⇒ **不扣分**、退回返工（轮次照计） |
| `/settle` | 维护者 | 态为 `verified` | 结算，按难度记正分入账本 |

补充口径（白箱、可核）：

- **「必带链接或证据块」**：载荷里出现 `http(s)://…` 链接，**或**评论正文里有围栏代码块
  （``` 里贴可复跑读数）——分析 / 复现类走证据块，修码类走 PR 链接。
- **「最多 3 轮修改」**：同一悬赏的第 4 次 `/deliver` 会被拒；此时请走 `/dispute` 交维护者裁定。
- `/verify`、`/settle` 是维护者动作的命令化（设计稿只写了「维护者打 `bounty:verified`」
  与 `verified → settled`，未指定触发形态）——若你希望改为纯标签操作，请在 issue 里提出。
- **审核员**（v0.1 新增）：`/verify` 与 `/appraise` 也可由**审核员**执行；`/settle` 仍只归维护者
  （**裁决与入账分离**）。**持有者一律回避**——不得自审自结（对维护者与审核员同等生效）。
  授权面＝账本 `role` 事件（append-only）；晋升走**复合判据**。详见
  [审核员机制 v0.1](../spec/审核员机制_v0.1.md)。

## 三、验收四闸（逐道可查 · 不通过就说不通过）

1. **CI 全绿**：该 PR 上本仓的门禁全绿（机器判，不可辩）。
2. **复现读数**：属「可复现缺陷」类 ⇒ 贴**原始读数**（改前 vs 改后逐项对照）。
3. **守卫 + 定点变异**：修码类必须带守卫件，以及「**注入必失败 ⇒ 断言必红并点名**」的
   定点变异自证（本仓既有惯例：判据不设反面证明就等于没有判据）。
4. **维护者人审**：维护者 `/verify` 给出判定与理由（含用哪份读数、哪些存疑）。

**防作弊**：交付必带**可复跑**读数；最多 3 轮修改；超时回板；声誉**可降**。

## 四、声誉计分（可追溯账本 · v1.0 质量化）

写入 `docs/bounty/ledger.json`（**append-only** 事件流；按事件 id 幂等去重）。每笔记分事件带
`formula` 快照（输入 + 中间值），**第三方仅凭事件本身即可复算**。

### 4.1 完成分（质量化）

```
delta = max(1, round_half_up(base × 2 / (round + 1)))     # round = 已发生的返工次数（首交付 0）
```

| `rounds`（1-based 交付次数） | `round` | 乘数 | expert | hard | medium | easy |
|---|---|---|---|---|---|---|
| 1（一次过闸） | 0 | 2× | 20 | 12 | 6 | 2 |
| 2 | 1（**中性点**） | 1× | **10** | **6** | **3** | **1** |
| 3 | 2 | 2/3 | 7 | 4 | 2 | 1 |

- **中性点＝返工 1 次**：此时 `delta == base`，与 v0.1 原分一致（等级标定不被隐性下移）。
- **舍入强制 half-up**（`floor(x+0.5)`），**禁用语言内置 `round`**——银行家舍入会在值恰为 `x.5` 时静默改分。
- ★ 本承载面 `max_rounds=3` ⇒ 第 4 次交付被直接拒 ⇒ **`round=3`（1/2 档）不可达**；上调 `max_rounds` 后自动可达，无需改公式。
- ★ `max(1,·)` 保底在本承载面**永不生效**（需 `rounds≥5`），保留以对齐标准。

### 4.2 扣分（按行为类型；扣分只有系统能记）

| 事件 | 分值 | 依据 |
|---|---|---|
| **超时未交付**（72h 回板） | **−2×base** | 未履约＝**行为不一致**，从重 |
| **轮次用尽**（第 4 次交付被拒） | **−base** | 判**无效交付**并转 `disputed`；努力过但质量不足＝行为一致，从轻 |
| `/verify fail`（退回返工） | **0（不扣分）** | **发布者不能凭一次不满扣分**——退回只计轮次 |
| 主动释放（`/withdraw`） | 0（不影响声誉） | — |
| 争议提起与败诉 | 0（**记录在案、不扣本金**） | — |
| 被拒命令 | 0（记在**尝试者**头上） | 刷单 / 重复认领的可查痕 |

⚠️ **超时从固定 −1 改为 `−2×base` 后幅度变化显著**：expert 超时 **−20**（原 −1）、medium **−6**、easy **−2**。

### 4.3 本承载面不适用项（显式声明，不得静默）

- ~~验收条目通过率 E~~ → **已启用（v1.0.1）**：`/verify partial <通过数>/<总数> <理由>` 给出逐条判定，
  分母进**标记快照**并随状态迁移继承（`criteria`），结算按 `E` 计；未给 `partial` 时 `E ≡ 1`。分母是维护者人审闸的判定、**随事件留痕可审**。
- **落选分（0/1/2/4）**：本承载面无竞标机制 ⇒ **不适用**。

### 4.4 分段生效与可复算

账本事件带 `rule` 字段：`v0.1`（固定分：虚假交付 −5／超时 −1）与 `v1.0`（质量化）。
**旧事件不回改**（append-only）；第三方可对任意时间点按**两侧常量**分段复算。
可复算入口：`bounty_board.rescore(events)`——逐条按事件自带 `formula` 重算并断言与 `delta` 一致。

### 4.5 招标模式与落选分（v1.1 · 参考招投标法）

打 `bounty:contest` 标签即开启**招标模式**（未打该标签时保持 `/claim` 独占租约，**向后兼容**）：

| 招标环节 | 本站实现 |
|---|---|
| 招标公告 | 打 `bounty:contest` 的 issue；**评标标准＝发布模板的「验收标准」栏**（预先公开） |
| 投标 | `/bid <PR 链接或证据块>`（**无需 `/claim`**，任何人可投） |
| **一人一投** | 同一人二次投标 ⇒ 拒（`duplicate_bid`）——**不得二次报价** |
| 投标截止 | issue 的到期时间（`due_at`）；**截止后不得投标或修改**（`bid_deadline_passed`） |
| 废标 | 不带链接或证据块 ⇒ 拒（复用 `_check_payload`） |
| 评标 | 验收四闸（第 ④ 闸是人审） |
| 定标 | `/select <中标人> <理由>`（维护者）⇒ 中标者转 `bounty:delivered`、`holder=中标者`、`rounds=1`（首交付） |
| **落标** | 定标时对**其余有效投标者**各记**落选分**：easy **0** ／ medium **1** ／ hard **2** ／ expert **4** |
| 异议 | 定标后走既有 `/dispute`（记录在案、不扣本金） |

- **落选分 0 分也写事件**：否则「投了但没中标」与「根本没投」在账本上同形，重标不可观测。
- 落选事件 `action=lose`、`formula.kind=lost_bid`，可被 `rescore` **独立复算**。
- **与 E 的关系**：中标者的交付照走 `/verify`（含 `partial p/t`）与 `/settle`，E 照常参与质量化。

荣誉榜 `docs/bounty/board.md` 由账本机械生成（不手改）。计分口径真源＝`scripts/bounty_board.py`
（`DIFFICULTY_SCORES` ／ `quality_delta` ／ `timeout_delta` ／ `invalid_delta`）；改口径只改那里。

**本站的差异点**（相对纯分数制）：本站在**可追溯的结构化记录**上结算——
「这个贡献者做过什么、交付质量如何」是**能查的**，不是一串数字。v0.1 先落公开账本；
更细的信任镜像面待裁定。

## 五、争议流程

1. 任一方在 issue 里 `/dispute <理由>`（持有者 / issue 作者 / 维护者）⇒ 转 `bounty:disputed`。
2. 维护者在 issue 线程内给出仲裁：**判定在前、读数对照在中、处置与边界在后**；仲裁结论以评论留痕。
3. 不扣本金，但争议记录在案（荣誉榜可见）。

## 六、参与方式

- **发布**（维护者）：用 [发布模板](../../.github/ISSUE_TEMPLATE/bounty.yml) 建 issue——**验收标准必填**、
  难度、期望交付形态、参考材料；维护者补 `difficulty:*` 标签。
- **认领**（任何人）：在该 issue 评论 `/claim`（首次认领前请读一遍验收标准——只按那份判）。
- **交付**：评论 `/deliver <PR 链接或证据块>`。
- **等验收**：维护者按 §三 四闸裁决；通过后 `/settle` 入账。

## 七、超时回板（自动）

每 6 小时扫描一次：`bounty:claimed` 且已过 72 小时未交付 ⇒ 自动回板 `bounty:open`
（回评说明原持有者、到期时间与超期时长；记 −1）。任何人可重新认领。

### 准入面（谁能设立悬赏）

三道，**自外向内**：

1. **模板不自动打标**：.github/ISSUE_TEMPLATE/bounty.yml 刻意不带 labels ——
   GitHub 会把模板 labels 自动加到**任何**开 issue 的人身上（无需写权限），
   而 bounty 是状态机准入闸，自动打标等于外部人可自授悬赏身份。标签一律**维护者手动打**。
2. **标签闸**（_check_claimable）：bounty 标签必须在 —— 管「这条是不是悬赏」。
3. **作者闸**（_check_admission）：issue 作者须 ∈ BOUNTY_MAINTAINERS —— 管「谁有权设立悬赏」。
   作者取不到（None）时**不放行**（fail-closed）。

**外部贡献申报**走 intake 命名空间（**不打** bounty）：它是**输入**，不是悬赏；
维护者裁定后由维护者**另立**悬赏。外部内容永远不会出现在悬赏面上。
