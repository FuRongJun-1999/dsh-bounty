## 二、怎么用

1. **看**：本清单是**统一查看面** —— 全部长期方向的验收标准、进度、负责人都在这里。改真源 悬赏.json ＋ 重跑 python -X utf8 scripts/bounty_list.py 即更新；产物有守卫与定点变异自证。
2. **认领**：本清单**本身不接受认领**（它只是查看面）。两个通道按条目分流，判据锚在**原 issue 的实际状态**（不由文本决定）：① 原 issue **仍开放**（带 `bounty` 标签、态为 `open`/`expired`，`issue_note` 写明「保留在 issue 通道」，如 #67/#68/#70/#71）——在该 issue 评论 `/claim`，状态机自动加 `bounty:claimed` 标签并登记租约；② 其余条目（原 issue 已 `CLOSED`、标签 `bounty:migrated`，载体已迁入本清单，如 eval-site / bounty-pm）——走 **PR 通道**：提交 PR 把真源 `docs/bounty/悬赏.json` 里该条 `status` 改为 `claimed`、`owner` 填你的 GitHub 登录名，并在 PR 描述里写明**执行计划（第一条复跑命令）**，同时重跑生成器更新本清单。为什么是两个通道：未认领方向的原 issue 已迁空关闭，`/claim` 在那里会被状态机按「无 `bounty` 标签」拒（并记在尝试者头上）；仍在办的条目保留 issue 通道以免打断活跃租约与在办提案。
3. **交付**：在 issue 上评论 /deliver <PR 链接或证据块>。证据须含**原始读数**（围栏代码块），逐项对应验收标准；未测的项**显式写「未测 ＋ 原因」**，留空或用「应该没问题」代替视为未交付。
4. **更新进度**：改真源 progress（追加一行，**不改历史行**）＋ 重跑生成器。
5. **两件事别混**：清单＝查看面（人读、机械生成）；issue＝**原 issue 仍开放的条目**的认领与交付状态权威面（状态机在跑）。**已迁入清单的条目**（原 issue 已关闭）其状态权威面＝本清单（真源 悬赏.json）。有活跃认领或在办提案的条目**不迁移**。

## 四、不适用条件（本清单在什么情况下不成立）

- **把清单当认领通道（针对原 issue 仍开放的条目）**：那类条目的认领走 issue（/claim），本清单对它们只是查看面。**反之，原 issue 已关闭的条目（`bounty:migrated`）认领只能走 PR 通道**（改真源 `status` / `owner` ＋ PR 描述写明第一条复跑命令）——见「怎么用」的「认领」。
- **单人自营、尚无外部贡献者**：清单仍可用（登记进度），但「认领」无对象。
- **不可机械复核的方向**（如「宣传效果好」）：**不得**写成悬赏——须先把它转成可核验的交付物（链接可达、读数可查）再登记。
- **涉资金的结算**：本站**不涉资金**，score 只是声誉分，不是金额。
- **手改产物**：悬赏清单.md 是机械生成的派生视图，手改会在下次生成时被覆盖。
