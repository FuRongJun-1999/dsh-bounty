# AI 编程工作流规范（插件测评合作者版）

> 版本 v1.0 · 2026-10-16 · 维护者：FuRongJun-1999
> 适用对象：参与 dsh 生态插件测评的外部合作者（含 AI 代理与人类）
> 来源：灵枢工作纪律 19 条（测评子集）＋ 悬赏站 118 件结算实战提炼

---

## 〇、一条总纲

**先查证、再动手；先取证、再下结论；写下的每个数字都要能复跑。**

这条来自 118 件结算的統計结论：凡是复审时「读数对不上原文」的申报，一律按
证据不可信处理；凡是「原始读数＋复现命令＋锚定提交」三件齐的，结算一次过。

---

## 一、测评工作流六阶段

### 阶段 1 · 准备（先查证再动手）

| 动作 | 判据 |
|---|---|
| 读目标插件 README 与 CHANGELOG | 确认版本号与安装方式 |
| 确认宿主版本 | 记录 dsh 版本（如 0.2.0-rc.2），拒绝装不上时不硬猜 |
| 建「锚定提交」 | 记录插件的 commit hash（如 @9c32d7a），全部结论只覆盖该提交 |
| 建工作目录 | `测试/<插件名>/`，原始输出存 `raw/` |

### 阶段 2 · 查重（反膨胀护栏）

| 动作 | 判据 |
|---|---|
| 搜悬赏站既有 issue | `site:github.com/FuRongJun-1999/dsh-bounty <插件名>` |
| 搜目标仓 issue | 插件名的变体、作者名、功能关键词 |
| 发现重复 | **主动撤回或合并**——撤回不是失败，是护栏合规（正面样本：@cyd471 #673 主动撤回 5 件） |
| 未见同件 | 在报告中写「查重：对照 X/Y/Z，未见同件」——要列你查过什么 |

### 阶段 3 · 执行（可复跑优先）

| 动作 | 判据 |
|---|---|
| 逐条跑、逐条记 | **每个动作一条原始读数**（命令＋退出码＋关键输出行） |
| 失败也要记 | 失败的命令＋完整 stderr，不要只写「失败」 |
| 双平台 | 至少 Windows＋WSL/Linux 各跑一遍；只跑一个平台要显式声明 |
| 基线对照 | 记录「无插件」的基线读数（如 #675 的 22~25s vs 1~3s） |
| 不猜根因 | 「未返回」≠「插件有 bug」——根因未定就写「根因未定」（#675 正面样本） |

### 阶段 4 · 取证（三件套）

每个结论必须能被第三方独立复跑。三件套：

1. **锚定提交**：插件 repo 的 commit hash＋日期
2. **复现命令**：完整命令行（含环境变量），任何人复制粘贴能跑出同读数
3. **原始读数**：命令的实际输出（不是你的转述——写「exit 1 + stderr 前三行」而非「安装失败」）

### 阶段 5 · 成文（诚实边界四态）

每个面向声明四种状态之一（缺一不可）：

| 状态 | 含义 | 正面样本 |
|---|---|---|
| **已验** | 跑过、有原始读数 | #565 五条修复各 20/0 守卫 |
| **未验** | 没跑，列原因 | #675「9 项未测显式列出」 |
| **不确定** | 跑了但读数歧义 | #736「低置信」标注 |
| **不做** | 主动排除，列理由 | #675「不排名、不给总分、不用星级」 |

**禁止**：只写结论不写读数；把「未验」写成「已验」；把「帮倒忙」写成「真有用」
（反样本：#731 P0——证据判「帮倒忙」、报告写「真有用」，被外部发现）。

### 阶段 6 · 交付（intake 通道）

用 `[intake 输入]` 前缀开 issue，正文顶部放 marker：

```html
<!-- intake:v1 {"project":"<项目>","difficulty":"<档>","impact":"<影响>","target":"<目标仓>","form":"intake"} -->
```

- `project`：memory / lingshu / bench / dsh_mobile_apk / chinese_programming / bounty_site / awesome_dsh_plugin / hive_memory_bench
- `difficulty`：easy / medium / hard / expert（词表外被校验器拒收）
- `impact`：A / B / C / D
- **不 /claim、不加 bounty 标签**——计分由维护者裁定
- 查重声明放在正文末尾：「对照 X/Y/Z 未见同件」

## 三、写代码时的守卫纪律

如果你交付的是代码（修复/功能），除上述流程外还需：

### 3.1 测试先于声明

```
python -X utf8 -m <你的测试模块>          # 全绿
python -X utf8 -m <你的测试模块> --mutate # 变异全红
```

- **恰好点红**：每个变异必须让**且仅让**对应断言失败——变异不红的守卫是假守卫
- 正面样本：@TanPowasd #85 的 11 条变异 0 条漏红；@rinDBeans #596 的 8 条变异逐项转红
- 反样本：#594——`field` 参数零使用、AST 判定可查，交付前自查即可发现

### 3.2 预注册（防调参）

如果是算法/模型类：
1. 先在 dev 集上**冻结配置**（写进文档）
2. 再跑 test 集
3. 报告里写「预注册于 X，验证于 Y」（正面样本：@TanPowasd #85「LoCoMo 英文 dev 预注册冻结后才上中文 hive」）

### 3.3 移植一致性

如果从原型移植：报告排序/输出与原型的逐位一致率（#85：92/92 排序、157/157 请求逐字一致）。

### 3.4 PR 纪律

- 基于**最新 main** 开分支——避免合并冲突（反样本：PR #395 提交后 main 推进多批，需 rebase）
- PR 描述含：改了什么／为什么／验证方式／边界与不做项
- CI 红了先修再催——「CI 永久红」不是「别人的问题」（反样本：#396 守卫大小写敏感）

## 四、工程实战经验（血泪清单）

以下全部来自悬赏站实战中的真实事故与修复：

### 4.1 文件与编码

- **一切命令统一走 `python -X utf8`**——Windows GBK 解码会让 stderr 变乱文，
  加 `PYTHONUTF8=1` 环境变量
- 读文件显式 `encoding='utf-8', errors='replace'`——偶数字节的 GBK/Latin-1 文件
  会让整个批处理 Traceback（#636）
- pwsh 管道（`| Select-Object`）在此环境会静默丢 stdout——用 Python driver +
  `subprocess.run` 逐条执行并自己打印

### 4.2 数据完整性

- **事件 id 是内容的 hash**——修改任何参与 hash 的字段（包括 formula）都必须重算 id，
  否则不变量 I2 检出（反样本：#293 formula 字符串 bug 被外部发现 #644）
- 账本写入与 gen/commit/push **分三步**——结算脚本的 `die()` 回滚会把已写好的
  账本一起还原（实战事故：#293 结算时账本被还原）
- 生成产物与手写产物**分开提交**——不要把 `site/` 手改

### 4.3 报告写法

- 数字要**逐字对账**：报告里写「134/134」就要能在证据块里找到那 134 条
  （反样本：#731——报告与证据脱钩被判 P0）
- 「未测」不是耻辱——显式列出比含糊其辞得分高（#675 的 9 项未测被点名为正面样本）
- 「不结论」比「错结论」好——A/B/C 根因未定就写未定（#675）

### 4.4 提交节奏

- **大批量先小批试**：先交 1~2 件看回执格式对不对，再交剩余的
- **一次一个 issue 一件事**：不要在一个 issue 里混装测评＋修复＋理论
- 关联 issue 用 `#编号` 引用，方便维护者跳转

## 五、禁止行为（扣分面）

| 行为 | 后果 |
|---|---|
| 抄袭他人申报（搬运不改名） | 扣分＋拉黑 |
| 伪造读数（不能复跑） | 事件作废＋扣分 |
| 明知重复仍提交（不查重） | 事件作废；重复 3 次以上扣分 |
| 高申低报（自评 expert 实际 easy 且无依据） | 按实际档结算＋记录 |
| 把「未验」写成「已验」 | 事件作废＋扣分（最重） |
| PR 里夹带无关改动（顺手改别的） | 退回重提 |

## 六、快速模板（复制即用）

### 6.1 测评报告骨架

```markdown
【测评报告】<插件名> <版本> 体验快测（<域> · 方法试验）

<!-- intake:v1 {...} -->

## 性质声明
本件是 intake 输入（外部贡献申报），不是悬赏：不 /claim、不自行加 bounty 标签。

## 锚定提交
<repo> @ <commit hash>（<日期>）

## 环境与基线
- 宿主：dsh <版本>
- 平台：Windows / WSL / Linux
- 基线（无插件）：<读数>

## 结果速览
| 面 | 结果 |
|---|---|
| 安装 | X/Y |
| 端到端 | X/Y |
| 自带测试 | X/Y |

## 逐项读数
（每项：命令 + 退出码 + 关键输出）

## 发现
（P0/P1/P2 分级，每条附复现命令）

## 诚实边界
- 已验：...
- 未验：...（列原因）
- 不确定：...
- 不做：...（列理由）

## 查重
对照 #X / #Y / #Z，未见同件。
```

### 6.2 修复交付骨架

```markdown
【贡献交付】<插件/仓> <改动摘要>（PR #N）

## 结论速览
| 条 | 缺陷 | 修法要点 |

## 复现（证据块）
python -X utf8 -m <test>          # X/Y
python -X utf8 -m <test> --mutate # N 条变异逐项转红

## 意图声明
（为什么这么修，不改会怎样）

## 边界与查重
（哪些没修、为什么；对照哪些 issue 未见同件）

## 最小性与副作用
（改了几个文件、无新依赖、不影响既有路径）
```

## 七、一句话总结

**每个结论可复跑，每个边界显式声明，每个重复主动撤回，每个数字逐字对账。**

做到这四条，你的申报在维护者眼里就是「一次过」的高质量件——结算快、定档高、
申诉无门。做不到，事件会被作废甚至扣分。
