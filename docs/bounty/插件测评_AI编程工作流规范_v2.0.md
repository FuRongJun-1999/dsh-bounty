## 一、插件测评怎么做（v2.0 改版：走网站）

一篇测评只给一个判定（五状态之一）；不给总分、不用星级；有结论的判定必须带可复核的证据链。
**流程与格式详见 [review.lingshulab.com/spec](https://review.lingshulab.com/spec)，线上提交在站内完成**——本节只保留要点速查：

1. 判定是五状态之一（真有用/帮倒忙/没啥差别/还说不准/没法测），与正文一致
2. 有结论的判定附 ≥1 条可点开的证据链接（配对 A/B 读数、门禁输出、复现步骤、日志；最多 10 条）
3. 档位决定能说什么：体验快测不出五状态、不进榜、禁「通过/合格」；标准测评＝配对对照＋统计判定；深度审计＝标准＋安全六威胁（未测就写未测）
4. 三条硬规矩：不给总分/星级；装不上就分开写「没法测＋安装失败」；未测就写「未测」，效果只管 90 天
5. 提交前过 /spec 的自查清单

## 四、悬赏通道实战经验（血泪清单，v1.0 沿用）

### 4.1 文件与编码

- **一切命令统一走 `python -X utf8`**——Windows GBK 解码会让 stderr 乱文；加 `PYTHONUTF8=1`
- 读文件显式 `encoding='utf-8', errors='replace'`（#636）
- pwsh 管道在此环境会静默丢 stdout——用 Python driver 逐条执行

### 4.2 数据完整性

- **事件 id 是内容的 hash**——修改任何参与 hash 的字段（含 formula）必须重算 id（反样本：#293/#644）
- 账本写入与 gen/commit/push **分三步**（实战事故：结算 die() 回滚把账本一起还原）
- 生成产物与手写产物**分开提交**——不手改 site/

### 4.3 报告写法

- 数字**逐字对账**：写「134/134」就要能在证据块找到那 134 条（反样本：#731 被判 P0）
- 「未测」不是耻辱——显式列出比含糊其辞好（#675 正面样本）
- 「不结论」比「错结论」好（根因未定就写未定）

### 4.4 提交节奏

- 大批量先小批试（1~2 件看回执格式）
- 一次一个 issue 一件事；关联用 #编号

## 五、禁止行为（扣分面，v1.0 沿用）

| 行为 | 后果 |
|---|---|
| 抄袭他人申报（搬运不改名） | 扣分＋拉黑 |
| 伪造读数（不能复跑） | 事件作废＋扣分 |
| 明知重复仍提交 | 事件作废；重复 3 次以上扣分 |
| 高申低报且无依据 | 按实际档结算＋记录 |
| 把「未验」写成「已验」 | 事件作废＋扣分（最重） |
| PR 夹带无关改动 | 退回重提 |

## 六、intake 通道（悬赏站特有，v1.0 沿用）

测评类交付若走悬赏 issue 通道（而非网站直投），用 `[intake 输入]` 前缀开 issue，正文顶部放 marker：

```html
<!-- intake:v1 {"project":"<项目>","difficulty":"<档>","impact":"<影响>","target":"<目标仓>","form":"intake"} -->
```

- `project`：memory / lingshu / bench / dsh_mobile_apk / chinese_programming / bounty_site / awesome_dsh_plugin / hive_memory_bench
- `difficulty`：easy / medium / hard / expert；`impact`：A / B / C / D
- **不 /claim、不加 bounty 标签**——计分由维护者裁定
- 查重声明放正文末尾
