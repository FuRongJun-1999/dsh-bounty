# 悬赏站长期任务 · 维护者运行手册 v0.1

> 本文是**维护者侧的周期性运行手册**，面向「持续处理悬赏站 issue 计分与 PR 复核」这一长期任务。
> 目的：把每一轮的处置变成**可复算、可复核、可交接**的固定动作，而不是靠人记得做。
>
> 权威边界：本文**不定义**计分口径（口径真源＝`scripts/bounty_board.py` 的 `DIFFICULTY_SCORES` /
> `quality_delta` / `timeout_delta` / `invalid_delta` / `loser_delta`），也**不定义**验收标准
>（验收标准真源＝各 issue 的悬赏条目正文）。本文只定义**流程**。

---

## 一、每轮固定动作（Round）

| # | 动作 | 产物 | 失败即停？ |
|---|---|---|---|
| 1 | **拉增量**：新增/变更的 issue 与开放 PR | 增量清单 | 否 |
| 2 | **PR 独立取证**（见 §二） | 逐笔判定单 | 是（该笔） |
| 3 | **出裁决**：合并 / 返工 / 不合并 | 裁决 + 理由 | 否 |
| 4 | **合并**（squash，保留原作者为提交作者） | 主干新提交 | 是 |
| 5 | **计分**：定档 → 归并工作项 → 写账本事件 | 账本增量 | 是 |
| 6 | **更新产物**：board / 贡献表 / 悬赏清单 / site | 产物 diff | 是 |
| 7 | **回执**：在对应 issue/PR 留复核意见与结算说明 | 评论链接 | 否 |
| 8 | **归档**：灵枢记忆（CCG 六要素 + 读回确认） | 节点 id | 否 |

## 二、PR 独立取证（第 2 步展开）——八道，缺一不算复核

1. **隔离克隆**：从**本地**仓 `--no-checkout` 克隆（不直连网络，规避限流）；
   设 `core.autocrlf=false` + `core.eol=lf`（宿主全局 `autocrlf=true` 会造成 CRLF 假红）。
2. **新守卫在自己的 head 上**：须**全绿**。（红 ⇒ 先查是不是栈式 PR，见 §三-3。）
3. **新守卫在修复前基线上**：只把测试文件拷到 `origin/main`，须**红**——
   证明判据真的锚在本次修复上，而不是空转。
4. **既有守卫全量回归**：`tests/*.py` 逐个直跑，非零 0。
5. **两道漂移闸**：`bounty_list.py --check` 与 `review_build.py --check`，均 rc=0。
6. **账本与产物未触碰**：`ledger.json` / `board.md` / `贡献表.md` 不得被该 PR 改动
   （除非该 PR 本身就是结算件）。
7. **集成**：把当前 `origin/main` 合进 PR head，判是否真能合。
8. ★**看删除行**：`git diff <merge-base>..<PR-head>` 里凡 `^-` 行含**他人**的逐笔留痕注释
   （`★本笔` / `★fix-`）⇒ 该笔在**静默回退**别人已合并的修复。
   仅看「head 自身绿」会漏判——已实证（见 §四-2）。

## 三、三类容易误判的情形（先排除，再下结论）

1. **口径文本碰撞**：改动若触及 `scripts/bounty_board.py` 里含「超时…−1」的句子，
   `tests/test_rule_text.py` 的 T2 会红。该守卫要求命中句**同时**含 `分段生效` 与 `v0.1`
   才豁免。**这是守卫正确，不是误报**；最小修法是保留 v0.1 历史常量、只让回评走 `timeout_delta`。
2. **命名混淆而非语义矛盾**：`rounds`（1-based 交付次数）与 `formula.round`（0-based 返工次数）
   是两个量。报「矛盾」前先把映射 `r = max(0, rounds-1)` 算清。
3. **栈式 PR**：新守卫在自己 head 上红，可能是它依赖**兄弟 PR** 的修复。
   先合兄弟 PR 再复跑，别直接判缺陷。

## 四、已知会静默漏判的三个盲区（每轮必查）

1. **改生成器源没重生成产物**：`SCORE_NOTE` 之类常量会经 f-string 进产物，
   而 `daily_table.py --check` 只做「渲染两遍互比」（确定性自检），
   `tests/test_daily_table.py` 的断言全在合成账本上跑——**没有一条读盘上产物**。
   ⇒ 源与产物漂移**无任何守卫会红**。
2. **静默回退**：见 §二-8。
3. **守卫扫描面与守卫目的相冲突**：`test_rule_text.py` 的动机原文举的例子是
   「以为超时只扣 1 分，实际扣 20 分」，而该例子正躺在被 `STALE_SCAN` **排除**的
   `docs/guide/**` 里。⇒ 读守卫时要**把「目的段」与「扫描面」并置读**。

## 五、计分归并口径（复述，非定义）

- 工作项归并：**一件工作 = 一条事件**。同一件工作拆在多个 issue/PR 上 ⇒ **并成一条**
  （先例：#165 并入 #164、#168–#170 并入 #156/#158/#159）。
  但**独立的两件工作即便同人、同源仓、同日也各记一条**——这是账本自身的实证常态：
  同 `(day, project, holder)` 有多条事件的共 **10 组**（如 `level0000x` 同日同仓 4 条、
  `LarryE135` 同日同仓 3 条）。
  ⇒「同人 × 同源仓 × 同日 = 1 项」这句话**只对「同一件工作」成立**，不可当成「一天只发一条」。
- 归并结果写进事件 `reason`，**不写进 `day`**。`day` = **结算日**
  （实证：`covers=[167]` 的 4 条工作项其创建日横跨 2026-09-23 / 10-11 / 10-12 / 10-13，
  而 `day` 一律为结算日 2026-10-13；创建日批次写在 `reason` 里）。
- 事件的 `issue` 取 `min(covers)`（实证：`covers=[83,84,90,91,100]` ⇒ `issue=83`）。
- `action` 恒为 `settle`；`actor` 恒为维护者登录名，干活的人记在 `holder`。
- `covers` = **本仓（dsh-bounty）的 finding / 申报 issue 号**，不是上游仓号；源仓标识走 `project`。
  取号分三支（**先判 finding 落在哪个仓**，别一律填申报件）：
  | 分支 | 情形 | covers 填什么 | 实证 |
  |---|---|---|---|
  | A | finding 就在本仓 | 各 finding 的 issue 号 | `[12,14,15,16,17]`（五条本仓 P0/P1 缺陷）、`[45,…,50]` |
  | B | finding 在上游仓，但本仓有对应【贡献申报】件 | 那些**申报件**号 | `[36,…,41]`（六件申报，finding 在 lingshu） |
  | C | finding 全在上游仓，本仓只有【验收申请】 | **验收申请号本身** | `[106]`（dsh-memory 回归审计）、`[107]`（hive-memory-bench 判分器审计） |
- **工作项归并的判据是「基线是否推进」，不是「同人×同源仓×同日」**（后者是启发式，会误并）。
  判「是不是同一件工作」：看后一批的**基线**是否晚于前一批 —— 晚于 ⇒ 前一批在物理上不可能覆盖它 ⇒ **新工作项**。
  实证：LarryE135 的 `#106` 与 `#273` 同人同仓同创建日，但 `#106` 基线 `23ac3f04`（10-12 23:59）、
  `#273` 基线 `0b5af358`（10-13 13:41），且 `#273` 所测的修复提交（`c1622694` 10-13 11:22、`5e9c313e` 10-13 12:46）
  **晚于 `#106` 基线** ⇒ 判为新工作项。另一例：acrot0 同日同仓已有 `covers=[65]`（交付测评站），
  其 `#269–#271`（修状态机授权/回避闸）仍另立一条 —— 不同种类的工作不算同一件。
- 定档依据（**含「为何不取自申档」**）必须写进事件 `reason`：申报件自申档位与件内逐条自申不一致时，取**可核验的那个**。
- 追溯性结算无轮次证据 ⇒ `round=1`（中性点，Δ = base）；
  有轮次证据且无返工且独立复核未见实质缺陷 ⇒ `round=0`（2×）。
- 影响等级按「**不做会怎样**」判，不按「做了多难」判。

## 六、每轮必跑的守卫清单（合并前 / 合并后各一遍）

```
python -X utf8 tests/<每个 test_*.py>          # 逐个直跑，非零即停
python -X utf8 scripts/bounty_list.py --check   # 悬赏清单漂移闸
python -X utf8 scripts/review_build.py --check  # 测评子站漂移闸
python -X utf8 scripts/bounty_board.py --ledger-append <events.jsonl>
python -X utf8 scripts/daily_table.py --ledger docs/bounty/ledger.json --out docs/bounty/贡献表.md
```

**账本复算自检**：`rescore(events)` 须 `ok=True`（0 条 bad）——这是账本可被第三方复算的唯一证据。

## 七、本文自身的边界（如实）

- 本手册是**流程描述**，不是判据：它本身**没有守卫**。若某轮跳过 §二 的某一道，
  不会有任何测试变红。**这是本手册当前的已知弱点**——补法是给关键步骤（如「删除行检查」）
  做成可跑脚本并纳入 CI，而不是靠这份文本。
- 本手册的 §四 三条盲区是**当前实测结论**，随守卫演进可能失效；失效时应更新本文并注明日期。

## 八、编制后新增实证（按日期追加，不改上文编号）

### 2026-10-14

1. **`base_of()` 要带前缀形态**：`base_of("hard")` **静默返回 1**（= `SCORE_DEFAULT`），
   正解是 `base_of("difficulty:hard")` ⇒ 6。账本里 `difficulty` 存**裸名**、`formula.base` 存数字，
   两者形态不同 ⇒ **从账本事件取难度再算分时必须先拼 `"difficulty:"` 前缀**。
   （生产侧不受影响：`build_state` 把 `difficulty` 存成**全标签** `difficulty:hard`，
   故 `base_of(st.difficulty)` 的 4 个调用点都对。此坑只咬从账本裸名起算的脚本。）
2. **修复类 PR 可能「零守卫」**：只改 `scripts/` 不改 `tests/` 的修复，合并后**没有任何守卫拦得住它的回归**。
   判据：`git diff --name-only` 里没有 `tests/` 路径。处置：修复正确 ＋ 回归绿 ⇒ 照合，
   但**回执里必须写明缺口**并建议补定点变异。另需查**同类既有实现是否也零守卫**
   （如 `_seq` 在测试文件里出现 0 次）——若也是，属**既有缺口**而非本笔引入，不该只挡本笔。
3. **与主干冲突且解法唯一时**：解冲突 → 全量验证 → **推回作者分支** → 再 squash 合并，
   并在回执里写明推了什么（`old..new`）与解法依据。解析冲突标记要**程序化**（逐行扫三段），
   **不要手写冲突块字面量**——冲突块常含反引号，会破坏脚本的模板字符串。
4. **入口形态先确认，再判缺陷**：`rescore` 是**库函数**不是 CLI；`--rescore` / `--since`
   在本仓**全部 git 历史里从未存在**（`git log --all -S` 空）。收到「复现命令」先跑一遍确认它成立，
   再判缺陷是否成立——**举证瑕疵 ≠ 缺陷不成立**，两者分开记。
5. **守卫能力数字（N 断言 / M 变异）写在 README 里但无守卫盯**：漂移是静默的。
   取数要**按套件适配**——`--list` 的前缀各套件不同（`M`/`N`/`R`/`S`/`E`），
   且有的套件 `--list` 打的是**断言清单**（`A01…`）而非变异清单；
   最可靠的是 `--mutate` 输出里的「共 N」字段。
   （2026-10-14 实测漂移：每日贡献表称 15 断言/4 变异、实为 **21/5**；悬赏清单称 16 变异、实为 **17**。已修 `48f765a`。）
6. **新增账本事件是廉价可逆的**：加事件**不改既有事件 id**（id 是内容寻址，只对**改写**敏感）。
   故定档争议时「先落账、后申诉改写」比「等裁定」更省事；但**改写**既有行会连带迁移引用面
   （见 `docs/bounty/账本id迁移_20261013.md` 的先例），代价高得多。
