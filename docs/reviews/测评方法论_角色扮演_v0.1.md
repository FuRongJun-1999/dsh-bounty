# 测评方法论 · 角色扮演方向（世界书触发＋上下文预算）v0.1

## 1. 一句话与范围

把**同一份规范世界书 ＋ 同一份对话历史 ＋ 同一组设置档**分别用手写基线与三家角色扮演方案各跑一遍，
取「激活集、注入顺序、预算裁剪、递归消融、深度消融、确定性、匹配口径消融、代价」八项读数，逐项对照。
读数全部由脚本落盘到 `bench/roleplay_eval/raw/`，报告只引用原始文本。

- 方向：**角色扮演**（roleplay），确定性面＝世界书触发（World Info）＋上下文预算。
- 被测方案（3 家）：SillyTavern、RisuAI、diceframe。
- 基线：`bench/roleplay_eval/adapters/baseline/run.py`（纯标准库手写实现，按 `bench/roleplay_eval/harness/CONTRACT.md` §2 的十条规则执行）。
- 只测**确定性、无 LLM** 的面；模型调用面一律未测（见 §9）。
- 运行期零网络、零凭据；不调用任何 LLM。

## 2. 为什么是这个方向（与既有两轮不相交）

本仓库 #67 已有两轮交付：

- 第一轮（记忆系统方向）：灵枢 / Mem0 / basic-memory。
- 第二轮（智能体工作流方向）：LangGraph / LlamaIndex Workflows / txtai。

本轮方向＝角色扮演，三家被测对象与上两轮无重叠。名称级交叉检索（在 8 个本地快照内检索
mem0、basic-memory、basic_memory、langgraph、llama_index、llamaindex、txtai，无源码级命中）
的过程与取证 URL 记在 `docs/reviews/选型取证_角色扮演_v0.1.md`。

三家之间相互独立，互相不构成 fork 关系：SillyTavern（JavaScript，AGPL-3.0）、
RisuAI（TypeScript，GPL-3.0）、diceframe（Python，AGPL-3.0）。

## 3. 工作负载（唯一夹具）

由 `bench/roleplay_eval/harness/make_fixture.py` 生成，生成器无随机数：同版本生成器必得同 sha256 产物。
三个产物：

- `data/worldbook.json`：25 条条目（uid1–23 为规范条目；uid24「正则键」与 uid25「内容宏」为能力探针；
  uid22 `enabled=false`；uid20 为正文约 900 字符的超长常驻条目）。
- `data/chat.jsonl`：12 条消息（`i=0..11`）；评估轮 turn k（k=1..6）＝只喂前 `2k` 条消息。
- `data/profiles.json`：P0–P4 五档（`scan_depth` / `recursive` / `budget_chars` / `case_sensitive` / `whole_words`）。

本机实测 sha256（`sha256sum`，读取 `bench/roleplay_eval/` 下的文件）：

- `data/worldbook.json` 的 sha256 = e5614804d895d0aee40a0d696589dccb844801773b9e6f8a85709e0f5407b093
- `data/chat.jsonl` 的 sha256 = e36f47a523868089d7c93dcb9744aec4dcf5b565b1c3ea799877fd4b3ac9efa5
- `data/profiles.json` 的 sha256 = 0856ea6d318153ba9f46ca6e02ff307f6c2174129917850e3e771360a494dd1c

字段语义、语义规范、输出契约、统一量尺、报告结构全部以 `bench/roleplay_eval/harness/CONTRACT.md`（冻结契约 v1）
为唯一接口定义。三家适配器只做字段翻译与读数格式化；触发、二级键、递归、成组择一、概率、排序、预算
一律由被测方自己的代码执行（依据见各适配器 README 与报告 §4）。

## 5. 公平性规则

1. **统一量尺**（CONTRACT §4）：`chars`＝Unicode 码点数（Python `len(s)`）；`bytes`＝UTF-8 字节数；
   `tokens(引擎)`＝各家自带 token 估算，属**方案内口径，不可跨引擎比较**，只允许出现在报告正文，不进读数行；
   激活集＝`active_uids` 集合；差异集＝同一 (档, 轮) 上两家的对称差；顺序差异＝同激活集上 `inject_order` 的逆序对数。
2. **同一夹具、同一档位、同一评估轮**：三家与基线读的是同一份 `data/` 产物（sha256 见 §3），
   同一套 P0–P4 档位，同一组 turn1–6；适配器只读 `data/`、只写 `out/`。
3. **字段映射表**：规范世界书字段 → 各家原生字段的逐条映射，写在
   `bench/roleplay_eval/adapters/diceframe/README.md`（第三节「字段映射表」、第四节「映射不上 ⇒ unsupported」、
   第五节「适配器侧口径声明」）与 `bench/roleplay_eval/adapters/risuai/README.md`
   （第四节「字段映射表」、第五节「档位字段映射表」、第八节「与基线的口径差异」）。
   映射不到原生字段的一律进 `unsupported`，不得用自写循环冒充引擎能力。
4. **预算口径差异**（四家不可直接比字符数）：
   - baseline：`budget_chars`，按 `content` 字符数累积，超出者跳过不截断；
   - diceframe：自有预算，`LoreRetriever._apply_budgets` 按引擎自己的字符估算口径裁剪；
   - SillyTavern：token，预算＝`max_context` 的 token 份额（`ENGINE_NOTE sillytavern profile=P0 max_context=16384 budget_tokens=4096 …`）；
   - RisuAI：自有预算，`char.loreSettings.tokenBudget`（上游按 token 计数）。

   ⇒ 同一档位在四家代表不同的量纲，**不得直接比字符数或激活条数**；跨方案只在「谁把哪条裁掉」这一层比，
   即 `dropped_uids` 集合（以及 P0 与 P3 之间的差集）。凡报告写 P3 的读数差异，必须同时写明该家的预算单位。
5. **能力不支持就写 unsupported**：字段级能力缺口逐条落在 `out/<name>_P*.json` 的 `unsupported`
   （`field` ＋ `reason`）与 `raw/<name>_P*.txt` 的 `UNSUPPORTED` 行；写「未测」不算缺证据，也不许留空。
   baseline 自己的 `unsupported` 字段是 `regex_key`、`macro_expand`、`tokenizer`、`upstream_commit`
   （四条 reason 见 `out/baseline_P0.json`）。
6. **读数行必须可逐字指认**：报告围栏代码块里以 `READOUT`、`DIFF`、`KPI`、`SHA`、`DETERMINISM`、
   `TIMING`、`CAPS`、`UNSUPPORTED`、`ERROR` 开头的行，必须能在 `raw/` 的某个 `.txt` 里逐字找到；
   引用 `raw/<文件>` 必须带扩展名且文件真实存在。
7. **不测厂商托管服务，不采集隐私数据**；夹具全部为自建合成内容；运行期不发起网络请求、不使用任何凭据。

## 6. 复现步骤（第三方原样可跑）

环境：Windows 11 ＋ MSYS2/Git-Bash（本机 `python` 3.13.13，CI 为 Python 3.12），`node` v24.16.0 ＋ `npm` 11.13.0。
所有命令的工作目录都是 `bench/roleplay_eval/`。安装期允许公开源（npm registry、Tsinghua pypi 镜像、
codeload.github.com）；**运行期零网络、零凭据**。

### 6.1 生成夹具（纯标准库）

```bash
cd bench/roleplay_eval
python -X utf8 harness/make_fixture.py
```

预期耗时：小于 1 秒；依赖体积：0（标准库）。产物即 `data/` 三个文件，sha256 见 §3。

### 6.2 diceframe（Python）

```bash
cd bench/roleplay_eval
bash adapters/diceframe/fetch_upstream.sh
bash adapters/diceframe/setup.sh
python -X utf8 adapters/diceframe/run.py --data data --profile P0 --out out/diceframe_P0.json
```

预期耗时与体积（本机实测）：codeload 下载＋解压 4 s、`python -m venv` 5 s、`pip install` 52 s（25 个包）；
`.venv` 66001 KB（≈64.5 MiB）、`upstream/` 25495 KB（≈24.9 MiB）。零 LLM SDK。

### 6.3 RisuAI（Node）

```bash
cd bench/roleplay_eval
bash adapters/risuai/fetch_upstream.sh
bash adapters/risuai/setup.sh
node adapters/risuai/run.mjs --data data --profile P0 --out out/risuai_P0.json
```

预期耗时与体积（本机实测）：下载 8 s（tgz 41,703,593 字节）、`pnpm install --frozen-lockfile` 11.5 s（本机 pnpm 仓为热仓；
冷仓同机实测 74.0 s）；`node_modules` 909,970,803 字节 / 33317 文件（867.8 MiB），上游＋依赖合计 969.0 MiB。
证据：`raw/risuai_timing.txt`。零网络复跑用 `--engine permissioned`（Node 权限模型不给 `--allow-net`）。

### 6.4 SillyTavern（Node ＋ 浏览器）

```bash
cd bench/roleplay_eval
bash adapters/sillytavern/fetch_upstream.sh
CHROME_PATH=/path/to/chrome bash adapters/sillytavern/setup.sh
node adapters/sillytavern/run.mjs --data data --profile P0 --out out/sillytavern_P0.json
```

预期耗时与体积（本机实测）：`npm ci` 17.3 s、`node_modules` 321.4 MB / 24366 文件、`tests/node_modules` 43.6 MB。
`npx playwright install chromium` 在本机解压阶段挂死（2/2 复现，证据 `spike/st-roleplay/SPIKE.md` §4.3），
因此必须用 `CHROME_PATH` 指向本机已装 chrome，`setup.sh` 与 `run.mjs` 都读该变量。
该适配器起本地 `node server.js --port 8123` 并在 chromium 页面里加载被测方自己的 `public/scripts/world-info.js`；
运行期只走本机回环地址，不请求任何模型 API。

### 6.5 五档批量跑＋落 raw/（四家同形）

```bash
cd bench/roleplay_eval
python -X utf8 harness/runner.py --adapter baseline    --profiles P0,P1,P2,P3,P4
python -X utf8 harness/runner.py --adapter diceframe   --profiles P0,P1,P2,P3,P4
```

`raw/<name>_runner.txt`、`raw/<name>_summary.json`。
预期耗时（本机 P0，min/p50/p95，逐字见各 `raw/<name>_runner.txt` 的 TIMING 行）：

### 6.6 契约校验、评分、跨方案对照

```bash
cd bench/roleplay_eval
python -X utf8 harness/validate.py out/diceframe_P0.json --strict-content
python -X utf8 harness/score.py --name diceframe
python -X utf8 harness/score.py --name risuai
python -X utf8 harness/score.py --name sillytavern
python -X utf8 harness/score.py --name baseline
python -X utf8 harness/cross.py
```

`validate.py` 校验 `out/<name>_<P>.json` 是否符合 CONTRACT §3.2（`--strict-content` 逐块比对注入正文的
字符数、字节数、sha256）；`score.py` 写 `raw/<name>_baseline_diff.txt`、`raw/<name>_diff.txt`、
`raw/<name>_kpi.txt`、`raw/<name>_summary.json`；`cross.py` 写 `raw/cross_matrix.txt` 与
`raw/cross_baseline_diff.txt`。这三个脚本都只读 `out/`、只写 `raw/`，重复运行产物逐字节相同。

### 6.7 独立复算（第三方验收入口）

```bash
python -X utf8 bench/roleplay_eval/harness/independent_recompute.py
```

该入口不采信任何已有读数：A 在系统临时目录重跑 `harness/make_fixture.py` 比对 `data/` 三个产物的 sha256；
B 按 CONTRACT §2 另写一份实现，独立算 `out/baseline_P*.json` 的 `active_uids` / `inject_order` / `dropped_uids`；
C 把 `out/<name>_P*.json` 每个 block 的 sha256/字符数/字节数与 `data/worldbook.json` 同 uid 条目的
`content` 重算比对；D 自算方案 vs 基线的逐 turn 对称差与 M1/M2，与 `raw/<name>_baseline_diff.txt`、
`raw/<name>_kpi.txt` 比对（浮点容差 1e-6）。stdout 逐字落在 `raw/independent_recompute.txt`。
退出码：全部 match 为 0，出现任一 false 为 1。依赖：仅标准库，无额外安装体积。
该入口的自身耗时不计入 M8 读数（M8 的耗时读数取自 TIMING 行）。

## 8. 不适用条件

本方法只对「确定性、无 LLM 调用」的世界书触发与上下文预算面成立，下列情形不适用，不得据本件读数选型：

1. 结论依赖模型输出质量（叙事生成、角色一致性、工具调用、消息归约、人工判断）的场景：本方法不含这些读数。
2. 语义检索与向量召回：夹具不含 embedding 通道，三家在该通道上都没有读数（各报告 §6 逐条列出）。
3. 与本夹具不同规模的世界书或对话：25 条条目、12 条消息、6 轮的读数不能外推到数千条条目或长会话。
4. 平台与版本：全部读数绑定本机（Windows 11 ＋ MSYS2/Git-Bash）、同一 Node 版本、同一浏览器与
   Python 3.13.13；计时绝对值不可跨机比较，只可同机对照。CI 的 Python 3.12 与其它操作系统上的行为未测。
5. 上游改动：读数绑定各家 commit（三家报告 §1 给出完整 40 位 sha）。上游若改动触发、排序或预算逻辑，
   对应读数与字段映射同时失效，必须按 §6 重跑而不是沿用。
6. 时间与计费：不含 token 计费、并发吞吐、多用户与托管部署面。
7. SillyTavern 的读数依赖本机浏览器与本地服务进程，不构成对纯 Node 环境下行为的结论。

## 9. 未测项与原因

以下各项在本次交付中**未测**，逐条给原因。三家的条目与其方案报告 §6 同源；每一家都可以在
`out/<name>_P*.json` 的 `unsupported` 与 `raw/<name>_P*.txt` 的 `UNSUPPORTED` 行上逐条指认。

1. **LLM 调用面：未测**。原因：任务硬禁联网与凭据；模型调用、采样、流式返回、错误重试都不在读数内。
   三家的 `engine_env` 逐字记为 `llm=none`、`network=none`（SillyTavern 另记
   `network=local-server-and-local-chromium-only`）。
2. **embedding 与向量检索通道：未测**。原因：需要 embedding 服务或模型权重；diceframe 在拿不到客户端时
   直接返回空候选，适配器传 `extra_candidates=None`；RisuAI 的 HypaV3 检索未接。
3. **浏览器依赖面：未测**。原因：SillyTavern 的读数依赖本机 chromium 与本地 `node server.js`；
   `npx playwright install chromium` 在本机解压阶段挂死（2/2 复现，`spike/st-roleplay/SPIKE.md` §4.3），
   改用 `CHROME_PATH` 指向本机 chrome。playwright 自带 chromium 路线、无头模式的差异、
   以及非 Windows 上的浏览器行为都未测。
4. **`unsupported` 字段逐条未测**：
   - baseline：`regex_key`（基线按字面键匹配，不执行正则）、`macro_expand`（基线不做内容宏替换）、
     `tokenizer`（基线无 token 估算）、`upstream_commit`（基线是本地实现，无上游提交）。
   - diceframe：`depth`（引擎不建模 ST 的 `depth`，条目级扫描窗口在引擎里没有对应字段）、
     `position`（引擎只接受 5 个 canonical slot 名，`before_char`/`after_char`/`at_depth` 落空，读数里的
     `position` 是夹具请求值回填）、`capability_probe`（夹具标记，引擎无对应字段）、
     `macro_expand`（`src/` 全库检索 `macro` 零命中）。
   - RisuAI：`probability`、`case_sensitive`、`group`、`group_weight`、`recursion.prevent`、
     `recursion.delay`、`capability_probe`、`budget_chars`、`recursive_max_depth`、`seed`
     （逐条 reason 见 `out/risuai_P0.json` 与 `adapters/risuai/README.md` 第六节）。
   - SillyTavern：`group_weight`、`recursion.delay`、`capability_probe`、`budget_chars`、`whole_words_cjk`
     （逐条 reason 见 `out/sillytavern_P0.json` 与 `raw/sillytavern_P0.txt` 的 UNSUPPORTED 行）。
5. **能力探针 uid24 / uid25 的部分面：未测**。原因：uid24 的正则键在四家的支持度不同
   （diceframe、RisuAI、SillyTavern 的 `capabilities.regex_key=true`，baseline=false），
   而夹具窗口正文里 `/地.图/` 都不命中，因此「正则键在同一夹具上的跨家可比读数」未取得；
   uid25 的内容宏只在 RisuAI 侧被 CBS 求值（用于 token 估算），扩展结果本身不记录，
   其余三家不做宏替换。
6. **上游自带测试套件与其它链路：未测**。原因：本轮只跑适配器链路；各家的其它模块
   （TTS/ASR/图像、角色卡导入导出、多 Book 绑定、SQLite 持久化、WebUI 与插件宿主）都不在读数内。
7. **跨平台、跨 Node/browser 版本、依赖裁剪后的最小足迹：未测**。原因：本机只验证同一台机器、
   同一运行时下的跨进程一致；`node_modules` 与 `.venv` 都是全量锁定安装，未做裁剪。
8. **最终消息数组组装、触发器脚本执行、角色卡导入导出链路：未测**。原因：本轮只调 SillyTavern 的
   `public/scripts/world-info.js`（`setWorldInfoSettings` ＋ `checkWorldInfo`），`inject_order` 只到该引擎
   返回的数组为止；这三条链路分别与请求层、UI 状态、文件选择器耦合，超出本轮读数边界。
