# 灵枢悬赏站 · 审核员机制（v0.1）

> 一句话：把「谁能裁决」从单人维护者扩到**可晋升的审核员**，并给所有裁决动作加**回避闸**
> ——持有者不得自审自结。
> 授权面**不是名单文件、也不是标签**，而是**账本里 append-only 的 `role` 事件**。

设计真源：[悬赏站设计 v1.0](悬赏站设计_v1.0.md)（§S5 承载面声明）。
机械件：`scripts/bounty_board.py` 的 `needs_recusal` ／ `roles_from_events` ／ `promotion_report`；
判据常量 `PROMOTION_RULES`（口径单点）；守卫 `tests/test_bounty_board.py` 的 `[R]` 组。
产物：[`../bounty/promotion.json`](../bounty/promotion.json)（晋升评估）／ [`../bounty/roles.json`](../bounty/roles.json)（授权面）。

---

## 一、为什么需要（三个已取证的问题）

1. **单人瓶颈**：`/verify` ／ `/settle` ／ `/appraise` 三个裁决动作全在维护者一人手上——
   贡献量一上来，裁决队列就堵在一个人身上。
2. **利益冲突（真缺陷）**：原实现**没有任何回避判据**——维护者若自己认领了某条悬赏，
   可以 `/verify` 通过自己的交付、再 `/settle` 给自己记账。取证：改动前全仓检索
   `recusal` ／ `回避` ／ `self_audit` **零命中**。
3. **没有晋升通道**：贡献者做完任务即止，不能承接裁决职责 ⇒ 社区长不出第二层。

## 二、三层授权（权限矩阵）

| 动作 | 贡献者 | 审核员 | 维护者 |
|---|---|---|---|
| `/claim` `/deliver` `/withdraw` | ✓ | ✓ | ✓ |
| `/dispute` | ✓ | ✓ | ✓ |
| `/verify` | ✗ | **✓** | ✓ |
| `/appraise`（价值评价） | ✗ | **✓** | ✓ |
| `/select`（招标定标） | ✗ | ✗ | ✓ |
| `/settle`（结算入账） | ✗ | **✗（刻意保留）** | ✓ |

**为什么 `/settle` 不给审核员**：**裁决质量**与**入账**分离——入账动账本、影响全局声誉分，
是维护者不可让渡的职责。审核员影响的是「判定」，不是「记账」。

## 三、回避闸（自审自结禁止）

- **判据**：`actor == issue 当前持有者` ⇒ 拒绝，机器码 `recusal_required`。
- **覆盖**：`/verify` ／ `/settle` ／ `/appraise` 三闸。
- **对维护者与审核员一律生效**：**授权不豁免回避**（审核员对自己持有的 issue 仍不得裁决）。
- 无持有者时不触发（开放态无人可回避）。
- 实现：`needs_recusal(st, actor)`——**纯函数、零 IO**，可离线复算。

## 四、授权面的承载（append-only）

**权威面 = 账本 `role` 事件**：

```json
{"id":"evt_<内容 sha1 前 12 位>","ts":"2026-10-12T20:00:00Z","issue":0,"action":"role","actor":"<授予者>",
 "subject":"<被授权者>","role":"reviewer|maintainer","op":"grant|revoke",
 "reason":"<依据：哪条判据、哪个读数>"}
```

> `id` 必填：`--ledger-append` 按 `id` 幂等去重（`append_events`），无 `id` 的事件**静默跳过**（CLI 仍打印"并入成功"）。
> `id` 格式为 `evt_` + 去掉 `id` 后事件内容的 sha1 前 12 位（见 `event_id()`），可手算也可先留空跑一遍再补。

- **同一主体以时间最晚的一条为准**：`op=grant` 留下、`op=revoke` 移出。
- 越界 `role` ／ 越界 `op` ／ 缺 `subject` 的事件**跳过**（不猜测）。
- **撤销只需追加一条 `op=revoke`**——不改写既有行（append-only 不破）。
- **授权面 = 启动面 ∪ 账本 `grant`，再减去账本最新态为 `revoke` 的主体**：
  名单（`Config.reviewers` ／ 环境变量 `BOUNTY_REVIEWERS`）只是**启动面**（提供初始授权，
  **不是权威**）——**撤销只需追加一条账本 `op=revoke`，启动面名单里的主体同样被撤销**
  （「撤销以账本为准」的落地；实现：`role_revocations(events)` ＋ `handle_issue_comment` 的
  `is_rev` ／ `is_maint` 两行）。
- **例外：GitHub 关联身份**（`OWNER` ／ `MEMBER` ／ `COLLABORATOR`）是**平台事实**，
  账本 `revoke` **不撤销**它——站内授权与平台身份分离，否则一条账本事件即可锁死仓主。
- 账本读不到时审核员面为空——**fail-closed**，不因读不到账本就放宽授权。

## 五、晋升判据（复合 · 建议值）

单阈值不够用：**声誉分只答「做了多难」，不答「做得多好」**。故用**复合判据**
（`PROMOTION_RULES`，改口径只改这一处）：

| 判据 | 建议值 | 理由 |
|---|---|---|
| 声誉分下限 | **24** | ≈ expert×2 ＋ hard×1，或 hard×4 |
| 已结算项数下限 | **2** | 防单次侥幸 |
| 一次过闸（`round=0`）占比下限 | **1/3** | 交付质量（**有区分度前置，见下**） |
| 无效交付上限 | **0** | 负向记录一票否决 |
| 超时未交付上限 | **0** | 同上 |

### 5.1 区分度前置：**轮次来源可辨**（关键）

「一次过闸占比」的前提是**轮次来源可辨**——`round` 到底是不是真实返工事实。两种来源：

| 来源 | 标记 | `round` 语义 |
|---|---|---|
| 状态机结算 | `formula.mode == "live"` | **返工事实**（`/deliver` 轮次计数 ⇒ `round = rounds − 1`） |
| 追溯性补记 | 无 `mode`（缺省） | **中性占位**（`round = 1`，非返工次数） |

- **有状态机事件** ⇒ 只用它算占比（分母 = 状态机事件数）；追溯性事件记入 `evidence_gaps`、
  **不进分母**。占比低于下限即阻塞。
- **只有追溯性事件** ⇒ 沿用既有口径：`round` 全为 `1` 时无区分度（不适用、不阻塞）；
  出现 `round=0` 或 `round≥2` 才算有区分度。
- 导出面新增 `round0_ratio_source`（`"live"` ／ `"retro"` ／ `null`）——
  **`null` 表示该条判据不适用**，此时 `round0_ratio` 也为 `null`
  （**不得报 `0.0`**：把「不可判」报成 0% 是误导）。

> 依据与 v1.0 §S5 同源（该处声明本承载面 `E ≡ 1`、质量条目维度不适用）：
> **占位值不是证据**——把中性占位当质量信号，会让判据在全员身上同时误报。
>
> **为什么必须按来源分流（缺陷 #267）**：旧口径拿「`round` 是否全为 1」当**代理**，
> 一旦同一人**混合**了状态机事件与追溯性占位，代理即失真——占比被占位稀释。实证：
> X ＝ 4 条全返工（低分）被判「无区分度 ⇒ 不阻塞 ⇒ 达标」，Y ＝ 1 次过闸 ＋ 3 次返工（高分）
> 反被阻塞 ⇒ **判据非单调**，且可被「先故意交一次坏活」博弈。按来源分流后两人都进分母，判据恢复单调。

### 5.2 证据缺口不阻塞，但必须显式确认

`evidence_gaps` 逐条列出（无 round 数据 ／ round 无区分度 ／ 有争议提起），
由授予者在 `role` 事件的 `reason` 里写明依据。**静默放行不允许**。

## 六、可复算入口

```bash
# 晋升评估（按人聚合声誉分／已结算项数／一次过闸占比／负向记录）
python -X utf8 scripts/bounty_board.py --promotion-out docs/bounty/promotion.json

# 授权面（role 事件 → reviewer/maintainer 名单）
python -X utf8 scripts/bounty_board.py --roles-out docs/bounty/roles.json

# 授予 / 撤销：向账本追加 role 事件（append-only、id 幂等）
python -X utf8 scripts/bounty_board.py --ledger-append <role_events.jsonl>
```

两者都**只读账本、纯函数**、确定性（同账本两次导出逐字段相同）。

## 七、本版不做（显式边界）

- **不提供 `/grant` 评论命令**：授予走账本追加，避免把授权面暴露成「一条评论即可触发」。
- **站内不展示审核员名单**：`roles.json` 已是产物，页面展示留待下一版。
- **不涉资金**：审核员是**职责**，不是收益位（本站声誉制、不涉资金，边界不变）。

## 八、不适用条件

- **单人自营、尚无外部贡献者**：审核员档无对象可授，回避闸仍生效。
- **无 `round` 区分度的追溯性账本**：一次过闸占比判据不适用（见 §5.1）。
- **争议败诉判据**：本承载面无「败诉」记录 ⇒ 不适用，争议须人审。
- **本机制不改写既有账本行**：历史事件一律不回改（append-only）。
