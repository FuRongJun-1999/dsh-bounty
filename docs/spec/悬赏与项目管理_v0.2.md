## 一、要缩小什么信息差

悬赏板的状态同时存在于**两个地方**：GitHub issue 上（标签 ＋ 评论里的机器标记）与本地
`ledger.json`（append-only 事件流）。两处各自可读，但**没有任何一件东西同时读两边**：

- 标签态是人眼视图，**可以被手改**（v0.1 已知：标记才是权威面，标签只是视图）；
- 账本态是机器写的，但**它不知道 issue 上的标签是否跟上了**；
- 结果是「账本记了 settle、issue 却还挂着 claimed 标签」这类**静默漂移**——

没有任何命令会因此报警，漂移要等某次人工盘点才被发现。

**本条的交付物就是那件缺失的校验件**：把两处放在一张表上对照，漂移**逐条点名**。

## 二、三方定义（先把词定死）

| 面 | 来源 | 读法 |
|---|---|---|
| **标签态** `label_state` | issue 的 `bounty:*` 标签 | 裸态名（`open` / `claimed` / …）；多个态标签 ⇒ 取 `STATE_LABELS` 声明序的第一个，并报「多态标签」 |
| **标记态** `marker_state` | issue 评论里的 `<!-- bounty:v1 {…} -->` | `seq` 最大且带 `state` 字段者；**权威面**（与 `bounty_board.build_state` 同序） |
| **账本态** `ledger_state` | `ledger.json` 的 `claim/deliver/verify/settle/withdraw/dispute/expire` 事件 | 按 `(ts, 追加序)` 取该 issue 最后一次态迁移的 `to` |

**有效标签态**（列名 `标签态` 列显示的值）＝ `标记态 or 标签态 or ("open" if 有 bounty 标签 else "-")`
——与 `build_state` 的优先级一致（**标记 > 标签 > 默认 open**），保证本件与状态机同尺子。

★ **声明态 vs 默认态（本件最要紧的一条口径）**：
「有 `bounty` 入选标记、既无态标签也无标记」时，态是**推导出来的** `open`，不是谁声明过的。
**默认态不要求账本背书**（否则线上每条刚挂上的 `bounty:open` 都会炸成漂移）；
只有**声明态**（态标签或标记）才要求账本有对应事件。⇒ `#76 只有 bounty 标签、账本无` = 一致，
`#76 带 bounty:claimed、账本无` = 缺账本事件。

**账本态是派生的、不是新增的**：`action → to` 映射

| action | to |
|---|---|
| `claim` | `claimed` |
| `deliver` | `delivered` |
| `verify` | `verified`（不驻留态；后续 `settle` 到达前账本记为 verified） |
| `settle` | `settled` |
| `withdraw` | `open` |
| `dispute` | `disputed` |
| `expire` | `expired` |
| `reject` / `role` | **不改态**（拒绝是尝试痕；role 是授权面） |

## 三、不一致分类（各自点名，不汇总、不静默）

**判据优先级：两面互相矛盾 > 单面缺件**。矛盾更严重，先报矛盾才不会被「缺件」把话抢走。

| 优先级 | 类 | 代号 | 判据 | 点名格式 |
|---:|---|---|---|---|
| 1 | **态冲突** | `STATE_CONFLICT` | 账本与**有效态**不一致，**且账本与标记、标签两面都对不上** ⇒ 问题在账本那面（如手工把账本 `settle` 改成 `claim`） | `#<号> 态冲突：标签/标记=<t> 账本=<l>（标签与标记均与账本不符）` |
| 2 | **缺标签** | `LABEL_GAP` | 账本有该 issue 的事件，但 issue 上**没有 `bounty` 入选标记**（或没有 `difficulty:*` 难度标签） | `#<号> 缺标签：<label>` 每缺一项一行 |
| 3 | **缺账本事件** | `LEDGER_GAP` | issue 上有**声明态**（态标签或标记），但账本里**没有该 issue 的任何事件**（或完全缺号） | `#<号> 缺账本事件：声明态=<态>（账本查无此号）` |
| 4 | **标记态冲突** | `MARKER_CONFLICT` | 账本与**标记**对得上（账本≡有效态），但**标签态 ≠ 标记态** ⇒ 标签过期或被手改；反之（账本≡标签）则消息里点明是**标记被手写** | `#<号> 标记态冲突：标记=<m> 标签=<l>（标签过期或标记被手写）` |
| 5 | **多态标签** | `MULTI_LABEL` | 标签面**自身**矛盾（同一条上并存多个 `bounty:*` 态标签） | `#<号> 多态标签：<a>/<b>` |

**为什么 4 与 1 分开报**：两者都是「某面与账本对不上」，但**该怪谁**不同——4 说明账本与权威面
（标记）一致、问题在标签视图；1 说明账本自己与两面都对不上。混报会让人误以为账本和标签各说各话。


补充口径（避免把正常情况报成缺陷）：

- `bounty:verified` **不驻留**（`bounty_board` 已知：verified 是过渡态）⇒ 账本 `verified` 与标签
  `delivered` 的差异**不算冲突**，只在「缺账本事件」面单独看。
- `expired` 在 MVP 同样不驻留（回板即 `open`）⇒ 账本 `expire` 事件后标签应为 `bounty:open`；
  标签仍是 `claimed` 才算冲突。
- `covers` 覆盖号（如一条结算覆盖 #24–#33）**不进三方表**——它们不是独立悬赏形态，
  逐号追责会把「一次结算覆盖十条」误报成十条缺标签。但摘要里**逐个列名**：只报个数等于
  「有号有嫌疑，但不告诉你是哪个」，那不是可复盘的点名。
- 只有账本、既无 `bounty` 标签也无任何账本事件的普通 issue **不代入**——本件只对账悬赏面，
  不对全仓 issue 池做全量审计。
- **态标签词表以 `bounty_board.STATE_LABELS` 为准**：本件**不自行扩充**。若线上出现了词表外
  的态标签（例如 `bounty:migrated`），本件按「无态标签」处理——**前提是该号仍带 `bounty` 入选
  标记**（带入选标记 ⇒ 仍在悬赏面上 ⇒ 会落进 `缺账本事件` 清点）；若某号连 `bounty` 都没有、
  账本也查无，则它本就不在悬赏面上，本件不代入（见「普通 issue 不代入」）。这条落差本身是
  **有用的信号**（意味着标签词表与状态机真源已漂移），改词表须改 `bounty_board`，不在本条范围。

## 四、对账表（`--dry-run` 的产物）

```
| issue | 标签态 | 账本态 | 是否一致 |
|---|---|---|---|
| #11   | settled | settled | 一致 |
| #66   | open    | -       | 缺账本事件 |
```

判据：**不一致项必须出现在表里，并另有一段逐行点名**（各类各一行、可 grep）。
退出码（`--dry-run`）：**0 = 校验件自身跑通**（含「有不一致」的情形）；1 = 账本结构坏 / 快照读不了；
2 = 用法错。**「有不一致」不是 `--dry-run` 的退出码**——否则 CI 无法区分「校验件坏了」与
「校验件报了真问题」。

## 五、执行面

```bash
# 离线对账（默认；数据源：--issues 指向的快照，缺省 docs/bounty/issues-state.json）
python -X utf8 scripts/check_plan.py --dry-run

# 显式给快照（快照格式见 §六）
python -X utf8 scripts/check_plan.py --dry-run --issues <path>

# 漂移检测（体例对齐 scripts/bounty_list.py --check）：
#   0 = 无漂移；1 = 检出漂移或输入坏。默认数据源＝仓内固定夹具（无网可跑）。
python -X utf8 scripts/check_plan.py --check

# 守卫 ＋ 定点变异自证（注入必失败 ⇒ 断言必红并点名）
python -X utf8 tests/test_check_plan.py
python -X utf8 tests/test_check_plan.py --mutate
```

**为什么另设 `--check`**：`--dry-run` 的退出码故意不报漂移（见 §四），于是 CI 若想「有漂移就红」
就没有抓手。`--check` 补这一格：**它只读仓内固定夹具**（`tests/fixtures/check_plan_golden*.json`），
所以**无网、确定性**；要拿线上数据跑它是运维动作（`check_plan_snapshot.py` 导出投影后
`--issues` 指过去），不进 CI。

**开关一览**（`--strict` 与 `--json` 是**正交**的：前者管退出码，后者管产物形态）：

| 开关 | 作用 | 退出码 |
|---|---|---|
| `--dry-run` | 打印全表 ＋ 各类点名 | 0（**即使检出漂移**）／1 输入读不到／2 用法错 |
| `--check` | 漂移检测（默认读仓内夹具） | 0 无漂移／1 检出漂移或输入坏 |
| `--strict` | **准入**：配合 `--dry-run`，检出漂移即 1（CI 用） | 同 `--check` 的映射 |
| `--json` | 产物换成机读 JSON（`schema=check_plan/v1`） | 同所在模式 |
| `--state <镜像>` | **离线状态镜像**（`bounty_board` 同格式：`issues{}` ＋ `ledger[]`）——**镜像即世界** | — |
| `--ledger` / `--issues` | 显式指定「账本 ＋ 快照」两件（**成对**） | — |

★ **输入读不到就响亮失败，绝不用样例冒充仓内实际状态**：`--dry-run` 在缺省输入
（`docs/bounty/issues-state.json` ＋ `docs/bounty/ledger.json`）不在时返回 1 并打印 `[error] …`，
**不**退回任何内置样例——原验收原文要的是「对**当前仓内实际 issue** 报表」，拿样例顶替是**撒谎**。
要在本机对一张真表跑，用 `--state`（`bounty_board --state board.local.json` 的同一格式）或
`--ledger/--issues` 成对指定。

★ **`--state` 与快照的差异（容易踩）**：镜像里 `markers` 存的是**已解析的标记字典**数组，
快照里 `comments` 存的是**评论文本**。本件把镜像的标记字典**重新渲染**成
`<!-- bounty:v1 {…} -->` 文本再解析，好让两条输入面走**同一条标记解析路径**（单一真源）。
另：`bounty_board.load_store` 对**不存在的路径返回空镜像**（它的设计是「本地演练起点」）——
本件**不照抄**那个语义：显式指定却读不到 ⇒ 报错退出 1，避免把「没数据」报成「无漂移」。

**机读口径** `check_plan/v1`（稳定结构，供下游自动化消费）：

```json
{"schema": "check_plan/v1",
 "rows": [{"issue": 8, "label_state": "claimed", "ledger_state": "-", "verdict": "缺账本事件"}],
 "defects": {"缺标签": [], "缺账本事件": ["#8 …"], "态冲突": [], "标记态冲突": [], "多态标签": []},
 "summary": {"issues": 7, "consistent": 2, "缺标签": 2, "缺账本事件": 2,
             "态冲突": 2, "标记态冲突": 0, "多态标签": 1, "covers_only": 2},
 "covers_only_nums": [10, 11], "drift": true}
```

- `verdict` / `defects` 的键就是上文五类名；`drift` 是 `has_drift()` 的布尔（= 各类计数是否有非零）。
- 结构**只增不改**：加字段是兼容改动；改键名或语义变动须升 `schema`。

## 六、快照格式（issue 面）

```json
{"source": "gh issue list --json number,labels,comments", "items": [
  {"number": 11, "labels": ["bounty", "difficulty:medium", "bounty:settled"],
   "comments": ["…<!-- bounty:v1 {\"seq\": 3, \"state\": \"settled\"} -->…"]}
]}
```

快照是**只读输入**：本件**不触网**（纯 stdlib，CI 不发网络请求）。取出投影的那一件是
[`scripts/check_plan_snapshot.py`](../../scripts/check_plan_snapshot.py)（需 `gh` 登录，**可选运维工具**，
产物**不提交进仓**——提交一份本地快照会让 `--dry-run` 悄悄依赖它，把「CI 能跑」变成「有网才跑得动」）。
运营机制（更新节奏/SOP）不在本条范围。

## 七、不适用条件

- **不在悬赏面上的 issue**：普通 issue（无 `bounty` 标签、账本无事件）不代入，本件不是全仓审计。
- **缺快照**：没有 issue 面数据时，本件只能报「无法对账」，**不得**把「读不到」当成「一致」。
- **替代状态机**：本件**不判命令合法性**（`/claim` 能不能过闸是 `bounty_board` 的事）；
  它只回答「两处记录是否指向同一态」。
- **资金/隐私**：不涉；只读本地账本与快照。
- **对内域（蜂巢 job）评分**：不在本条范围（协作架构 v0.2 第七章）。
