## 〇、结论先行

**一句话**：v1.0 的声誉分回答的是「**做了多难的活**」（`base` 1/3/6/10 ＋ 落选分 ＋ 扣分）；本设计补上「**做得多好**」——**把贡献评价从单维标量扩展为可独立复算的指标向量**，且**不破坏** v1.0 的任何既有纪律（系统唯一写入／append-only／幂等可对账／发布者不能单次扣分／不涉资金）。

**三原则的硬判据（各一句话，可检验）**：

| 原则 | 硬判据 | 违反的样子 |
|---|---|---|
| **公平** | 单次 `delta` **只由 `base` 与公开规则决定，不读任何历史量**（历史分／Lv／过往轮次）；Lv 只给**容量**（可接任务数），**不给优先选中权** | 按历史分加权决定单次分；Lv 影响候选排序 |
| **公正** | 每条变动要么**可复算**（输入在事件表）、要么**人审留痕**（必填理由）；**争议只追加事件、不改历史** | 发布者单方扣分无需理由；争议中修改或删除历史事件 |
| **公开** | **任何人拿公开数据（规则常量表 ＋ 事件表 ＋ 交付元数据）能独立复算出同一个数** | 只公布总分不公布事件表；公布公式但不公布常量 |

> **「公开」不等于「公开源代码」**——公开的定义是**外部第三方在不接触内部系统的情况下能复算出同一个数**。复算必须依赖内部私有中间态才能得出的分数，不算公开，只是宣称公开。

**冲突优先级（采纳撰写单元的裁定）**：**公开 > 公正 > 公平**。理由：不可复算则公平与公正都无从被外部检验；公正是程序底线（谁能写、有没有理由），破了系统不可信；公平是可调的分配规则。

**核心推荐：质量用「加式」而非「乘式」**：
- 乘式 `delta = max(1, round(base × Q × E))` 会**反转难度梯度**（hard 一次过 6 > expert 三轮过 4，"差"翻盘"难"），且**系统性下移全员分数**——而 Lv 阈值（`10×n(n−1)/2`）与 `max_concurrent_tasks` 都是按 1/3/6/10 标定的，等于**隐性改动 v1.0 的等级制度**。
- 加式 `delta = base + max(0, round(base × (Q × E − 0.5)))` **梯度单调**、**新人保护**（三轮过闸不低于原分，只欠加分），且把「多难」与「多好」拆成可分别复算、分别上榜的两个维度。

**一条必须先说清的边界**：v1.0 定「**不接 GitHub、不读 PR、不记录 PR 元数据**」⇒ 本设计**全部输入只来自站内数据**。被砍掉的"看起来很好但拿不到"的指标（改动行数／CI 结果／覆盖率 diff／上游是否回滚）已逐条列在 §一·1.3；可替代的只是**交付过程的站内可核事实**，**不是代码质量**——本设计只承诺复算前者，不替它宣称后者。

## 一、现状盘点：v1.0 已有什么、缺什么

### 1.1 已有什么（不重造）

1. **base**（easy 1／medium 3／hard 6／expert 10）— 贡献评价的**唯一主维度**：难度标量，只回答"做了多难的活"。
2. **团队摊薄** `max(1, round(base × (1 − 0.2×(n−1))))` — 折算多人分同一份活，防人头通胀。
3. **落选分 1/2/3/4（按难度）** — 承认"提交过有效交付但未被选中"的劳动，避免竞争型任务把失败者归零。
4. **阶段折算** `max(1, round(base × ratio/100))` — 按 milestone 粒度部分结算，使"完成一半"可被承认。
5. **扣分通道**（超时未交付 `−max(1, base//2)`／无效交付 `−base`／admin_adjust 必填理由）— 唯一的负向维度，但只有两档语义。
6. **发布者不能单次扣分**（退回返工不扣分、只计轮次，默认上限 3 轮）— 把"质量争议"从发布者自由裁量里摘出，抗单边滥权。
7. **不产生声誉的事件清单**（withdraw／cancelled／争议提起与败诉／被拒命令／未核销 = 0）— 堵住"刷事件凑分"。
8. **系统唯一写入 + ReputationEvent 唯一约束 + recalc_stats + 断言 `user.reputation_total == sum(events.delta)`** — 幂等、append-only、可对账。这是本设计"可独立复算"的**地基**。
9. **等级阈值与权益表**（个人 `T(n)=10×n(n−1)/2`；团队 `30×n(n−1)/2`；benefits 现只有 `max_concurrent_tasks`，加权益不改代码）— 把分转成"可接多少活"的制度出口。
10. **榜单**（声誉榜 + 累计赏金榜，各含永久榜与自然月榜；不做团队榜）— 公开面的既有出口，也是缺口 (c) 的落点。

### 1.2 缺口逐条

(a) **质量不可区分**。`tasks_submission.round` 已记轮次、`status` 已区分 `approved/rework/rejected`，结算却只看 base：0 轮过闸与 3 轮返工后过闸**同 delta**。破坏**公正**——同酬不同质，"一次做对"与"反复救火"在账本上无差别，返工的边际代价为零。

(b) **验收条目通过率未入分**。v1.0 要求发布时写可复核验收条目，`tasks_claimmilestone` 有逐里程碑状态、`tasks_submission` 有 `review_comment`，数据在手却未进计分。破坏**公正**——验 8 条与验 10 条同分，验收条目退化成形式条款。

(c) **月榜缺归一化口径**。自然月榜按**绝对分**排序。破坏**公平**——接得多者恒胜，榜上比的是体量（接单机会）而非单位贡献质量，对受 `max_concurrent_tasks` 约束的低 Lv 新人系统性不利。

(d) **诚实性无指标**。如实声明"未取证／不适用"的交付不被奖励，虚报只在大错（判无效交付）时才被扣。破坏**公正**且**反向激励**：诚实零收益、谎报是低频高收益的赌注，账本看不到"这个人的交付是否可信"。

(e) **协作性无指标**。评审他人交付、替他人复现证据、指出他人交付里的问题，均无分。破坏**公开**——公开面看不到"这份交付被谁复现过、谁的评审改变了结论"，协作行为不进账本便不可追溯。

(f) **团队分配透明度**。`tasks_allocation.is_participant` 由**队长勾选**决定入选者，`reputation_granted` 随人数摊薄而每人不同，却**没有可公开的分配判据**。破坏**公开**——外部人拿到公开数据也复算不出"为什么是他而不是他"。

### 1.3 一条边界

v1.0 定：「**不接 GitHub、不读 PR、不记录 PR 元数据**」。推论：本设计全部输入只允许来自**站内已有数据**（事件表 + 交付记录 + claim／milestone／submission／allocation），`docs/spec/悬赏站设计_v1.0.md` 之外的一切托管侧读数**一律不可用**。

被砍掉的"看起来很好但拿不到"的指标：**改动行数／文件数／提交数／commit 粒度**（最常被误当质量的工作量代理量）；**CI 结果**——悬赏板参考稿的"CI 全绿"闸与"守卫 + 定点变异"闸，读数都在托管侧，本站取不到；**PR 审阅意见数、评审人身份、首次响应时长**（协作性最顺手的外部代理量）；**覆盖率 diff、重复率、静态告警数**；**改动是否被上游回滚**。可替代的只剩站内事实：证据包自述、里程碑逐条状态、`submission.round`、`review_comment`、发布者判定、争议记录。须点明：这些**不是**"代码质量"，只是"交付过程的站内可核事实"；本设计只承诺复算后者，不得替它宣称前者。（未取证：站内验证明细是否足够细，待核 `tasks_submission`／`tasks_claimmilestone` 实际字段。）

## 二、指标向量：把"多难"与"多好"分开

### 2.1 设计原则

① **可查**：每个指标的输入必须能定位到具体字段与行（如 `tasks_submission.round`、`tasks_claimmilestone.status`）；定位不到就不做。② **可独立复算**：**硬判据**——任何人拿到公开数据（事件表 + 交付记录）能算出同一个数；算不出来就不是公开，只是宣称公开。③ **不引入不可复现的主观量**：无"态度""印象""沟通感受"，只用枚举、布尔、计数与已公示整数。④ **不破坏 v1.0 纪律**：仍系统唯一写入、append-only、幂等可对账、发布者不可单次扣分、不涉资金；新指标只能作为**新事件类型**落账，不新增写入者。

### 2.2 质量系数 Q

| `submission.round` | 语义 | Q |
|---|---|---|
| 0 | 一次过闸 | 1.0 |
| 1 | 返工 1 轮后过闸 | 0.8 |
| 2 | 2 轮 | 0.6 |
| 3 | 3 轮（上限）后过闸 | 0.4 |
| 轮次用尽仍未过 | `rejected` | 不走 Q，按既有无效交付 `−base` |

输入来自 `tasks_submission.round`（计数）与 `tasks_submission.status`；以该 claim／milestone 结算时刻的 `round` 为准，落账后不可改（append-only）。**不双重惩罚**：`rejected` 已由 v1.0 扣 `−base`，Q 不再叠加。

### 2.3 验收条目通过率 E

`E = 通过条目数 / 条目总数`；分子分母都是计数（发布时声明的验收条目 × 逐条判定状态），不含人工打分。**缺失时不许静默当满分**：发布时未写条目 ⇒ E 记 `null`、事件打 `quality_unverified=true`，该笔**不进质量榜、不参与月榜的质量维度**，公开面明示"质量未计量"（E 不取 1.0）；条目已写但部分未判定 ⇒ 分母为声明条目数，**未判定按未通过计**（保守口径），被扣方可走 v1.0 既有争议通道，判定覆盖率随事件公示。

### 2.4 合成方式：取舍与推荐

**乘式** `delta = max(1, round(base × Q × E))`：可解释性最强（一步三因子，形态同 v1.0 的 `max(1, round(...))`）；但**难度梯度会被反转**——hard 一次过 `6` > expert 三轮过 `max(1, round(10×0.4)) = 4`，"差"翻盘"难"，激励转向挑容易的活做干净；**新人保护弱**——质量差者被直接乘掉，且 easy 档 `max(1, round(1×0.4)) = 1` 与一次过同分，低档分辨率被 `max(1,…)` 抹平。

**加式** `delta = base + B`，取 `B = max(0, round(base × (Q × E − 0.5)))`（`Q × E = 0.5` 为**基准质量**，高于基准才加分；低于基准不加分也不扣分，扣分仍由 v1.0 超时／无效通道负责）：**梯度单调**——expert 0 轮 `10+5=15` > expert 三轮 `10+0=10` > hard 0 轮 `6+3=9` > medium 0 轮 `5` > easy 0 轮 `2`；**新人保护强**——三轮过闸拿到不低于 v1.0 的分，只欠加分；**可解释性**同样一步可复算（0.5 与 Q、E 全公示），代价是质量上限仅 base 的 50%。

**推荐加式**：① 难度是发布者／管理组定的**客观档位**，不该被质量乘掉，否则账本从"承认难度"变成"惩罚难度"；② 乘式系统性下移全员分数，而 Lv 阈值与 `max_concurrent_tasks` 均按 1/3/6/10 标定，等于**隐性地改了 v1.0 的等级制度**，违反"不破坏既有纪律"；③ 加式把"多难（base）"与"多好（Q×E）"拆成可分别复算、分别上榜的两个维度，正合本章命题。取 0.5 为基准的用意即：让"返工到上限仍全过"≈ v1.0 原分，避免对存量分系统性下移。**代价照实说**：加式下返工只少加分不扣分，高质量激励偏弱，缓解是把**质量单独出榜公示**，并把 0.5 作为可调数据。（未取证：两个口径对存量账本的迁移影响尚未回放实算。）

### 2.5 负向指标（只做可复算的）

- **虚报证据**：交付自述与站内可核字段矛盾（如自称完成 3 个里程碑而 `tasks_claimmilestone` 仅 1 个），须附证据指针（submission id + 字段对照）⇒ `−max(1, base//2)`。
- **证据不可复跑**：复现者按证据包步骤执行得不到同结果，且经管理组确认 ⇒ `−max(1, base//2)`。
- **争议败诉**：v1.0 已定 0 分（只记录在案），本设计**维持不扣本金**，仅落 `dispute_lost` 事件供质量榜与内部权重使用；若日后裁定改为扣分，上限同 `−max(1, base//2)`，且与虚报**取最大值、不叠加**。
- **单任务负向总额 ≤ base**（与"无效交付 −base"同级），防分被打穿或叠加荒谬扣减。
- **不做**：主观"态度扣分"（响应慢、措辞、沟通风格）——不可复算，一旦引入即摧毁"任何人可复算"的判据。

### 2.6 协作分 C（可选维度）

留痕方式：在事件表新增 collaboration 事件——第三方在自己账号下对该 submission 提交**复现报告**或**评审意见**并给出结果标签（confirmed／refuted／partial）。计分：只计**被发布者或管理组采纳为有效**的复现／评审（单纯自述不计），每条 `+1`，每人单月上限 5；C **不进 delta**，保持 v1.0 的分数与阈值标定不变，只作独立"协作榜"维度（是否折算待裁）。

防刷判据：① **对偶限制**——若 A、B 在同期互评且各占对方 C 的 >50%，标 `reciprocal_suspected`，C 保留留痕但不计入榜单归一化；② **结果相关性**——仅"改变结论"的意见计分，即该交付因之发生 `rework`／`rejected`，或 `review_comment` 非空且 `status` 变更；③ **去重与上限**——同一 submission 每人只计一次、单 submission 最多计 3 条；④ **资格限制**——该 claim 的参与账号不得为自己的任务计 C（不能自评、不团队内互计）。

## 三、公平 / 公正 / 公开：三原则的可构造判据

原则不可检验就是口号。本章每条判据都配一个**可构造的检验**：给它一个输入，它能红。共同量纲先约定：单次结算分记作 `delta`，由 `base`（难度：easy 1 / medium 3 / hard 6 / expert 10）经公开规则折算；`delta` 的**计算纪律**不因引入指标向量而放宽。

### 3.1 公平（fairness）

- **F1 同难度同工同酬**：`delta` 只由 `base` 与系统规则决定，不读任何历史量（`reputation_total`、`Lv`、过往轮次）。
  *检验*：构造接赏者 A（高分老手）与 B（新人，0 分），二者对同一 `difficulty=hard` 的同一 `milestone` 均一次过闸 → 断言 `A.delta == B.delta == 6`。若 A > B，公平失效。
- **F2 权益不与身份/历史绑定**：`Lv` 只映射到容量 `benefits={"max_concurrent_tasks": N}`，**不含「优先选中权」**——选人权在发布者。
  *检验*：对调 A（Lv.10）与 B（Lv.1）的 `Lv`，断言发布者可见的候选 `claim` 集合不变；若任何接口返回「按声誉排序的候选列表」，即失效。
- **F3 新人保护**：落选分按难度 1/2/3/4，**最低 1 分保底**。
  *检验*：断言所有难度下有效交付落选者 `delta ≥ 1`；并验不倒挂——easy 落选 1 与 easy 完成 1 持平，expert 落选 4 < expert 完成 10。
- **F4 避免马太**（月榜归一化、团队分摊）：
  *检验（团队）*：队长勾 n=3 人、`base=hard(6)` → 每人 `max(1, round(6 × (1 − 0.2 × 2))) = 4`；断言 n 增大时每人分单调不增且恒 ≥ 1。
  *检验（月榜）*：三个月各 3 分者 vs 一个月 9 分者 → 自然月榜后者在前、永久榜前者在前；若两者名次完全相同，归一化未生效。

### 3.2 公正（justice）

- **J1 系统唯一写入**：只有系统规则与 `admin_adjust`（留痕）能产生 `ReputationEvent`；发布者只能经「选中/完成」**间接**加分。
  *检验*：以发布者身份遍历全部对外写接口（选中/完成/退回返工/提交），断言 `user.reputation_total` 与事件表条数均不变；能改分的路径只有事件表写入口。
- **J2 可复算或留痕**：每条变动要么带复算输入（`base`、`difficulty`、`ratio`、`round`、n），要么带人审理由。
  *检验*：对每条事件断言 `recomputed(delta) == delta`；对 `admin_adjust` 事件断言理由非空，空理由即为违规事件。
- **J3 发布者不能凭一次不满扣分**：点「退回返工」**不扣分**，只计轮次（默认上限 3）。
  *检验*：同一 `submission` 被 rework 1/2/3 次 → 断言该任务累计 `delta == 0`；第 4 次（轮次用尽）才落 −`base`。若第 1 次 rework 就出现负 `delta`，失效。
- **J4 争议只追加、不改历史**：争议提起/败诉记 0；撤销走 `admin_adjust` 追加。
  *检验*：先落一条 −hard 的事件，再落一次争议胜诉的 `admin_adjust` +6 → 断言事件表长度 +2（原 −6 仍在）、复算总分为 0、且不存在任何 update/delete（append-only 断言）。
- **J5 admin_adjust 可复核**：必填理由，操作者与理由在公开面可见。
  *检验*：空理由提交 → 拒绝；成功后该事件含理由与操作者。

### 3.3 公开（openness）

- **O1 可独立复算**：任何人拿公开数据算出同一个数。
  *检验*：只给第三方 (a) 规则页常量表、(b) 公开事件表、(c) 交付元数据（`round`、`milestone` 状态、是否落选），手算某 `user` 的 `reputation_total`，必须与站内一致。反向必失败检验：改动规则页任一常量（如落选分表 1/2/3/4）却不重生成榜单 → 第三方复算值 ≠ 站内值，对账断言必红。
- **O2 对账断言**：`user.reputation_total == sum(events.delta)`，由 `recalc_stats` 独立复算。
  *检验*：重复投递同一条 `ReputationEvent`（幂等键＝事件 id）→ 断言 sum 与缓存均不变。
- **O3 公式入 rules 页、榜单机械生成**：榜单由账本生成，不手改。
  *检验*：手改榜单后重跑生成器 → 输出被覆盖为与账本一致，diff 为空。
- **O4 「公开」不等于「公开源代码」**：公开的定义是**外部第三方在不接触内部系统的前提下能复算出同一个数**。若复算必须读内部私有评语或审核中间态，则只是宣称公开，不满足 O1。

### 3.4 三原则的冲突与优先级

典型冲突：F1「同工同酬」与「按实际质量给分」。裁决顺序：**公开 > 公正 > 公平**。理由：不可复算则公平与公正的裁决都无从被外部检验；公正是程序底线（谁能写、有没有理由），破了系统不可信；公平是可调的分配规则。处置口径：质量只能表达为**结算前就写进验收标准的公开增量**（如是否一次过闸、轮次），不得由发布者事后裁量；改质量权重必须**先改规则页常量再生效**。另一冲突：团队分摊（F4）与对账（O2）——以每笔 `allocation` 各自成事件、sum 守恒收口，不设两套数。

### 3.5 反例清单（明确违反三原则）

- 违**公平**：按历史分加权决定单次 `delta`；`Lv` 影响选中或候选排序；团队任务队长独占 `base`、参与人 0 分。
- 违**公正**：发布者单方扣分无需理由；争议处理中修改或删除历史事件；`admin_adjust` 无理由、不公开操作者。
- 违**公开**：只公布总分不公布事件表；公布公式但不公布常量（落选分表、分摊系数 0.2、轮次上限）；榜单手工维护、与账本不一致。

## 四、与灵枢内部信任值的同构映射

### 4.1 两套信任的现状

对外＝悬赏站的公开声誉分 `reputation_total`：`ReputationEvent` append-only 事件流聚成，系统唯一写入，幂等可对账（见 docs/spec/悬赏站设计_v1.0.md §4.4）。
对内＝灵枢大脑库连接层的对端信任 `p_trust`（md_cg/links.py），四条性质：**概率估计非承诺**（可被反例击穿）；**有上限** `p_trust_cap`（受版本对齐度与节点完整度约束）；**有衰减**，`DECAY_DAYS=30` 无观测向初值回归；**全程留痕**（audit，宪章第二十四条）。写向唯一入口 `observe(peer, evidence, positive)`，正 `UP_STEP=+0.05`、负 `DOWN_STEP=−0.20`，跌破 `DEGRADE_BELOW=0.50` 自动降级 degraded。诚实边界：`UP_STEP`／`DOWN_STEP`／`DECAY_DAYS`／`PROBATION_SECONDS` 均为**未标定占位值**（标定属路线图 v0.3）。

### 4.2 为什么要映射

对外声誉**公开可查**，对内信任**本机私有**（连接层落盘文件 0600）。两者不接，则「在悬赏站做得好」不会改变「内部系统愿意把活派给谁」；公开面的努力无对内回报，两套信任各自漂移。

### 4.3 映射设计（单向）

只允许**公开声誉 → 内部信任**，以结算事件为证据经 `observe` 推入；**禁止反向**——内部 `p_trust` 不得出现在公开面（工作纪律第 9 条敏感信息隔离／第 14 条内容政策合规）。

- **进 observe**：`verified + settled` 的结算事件 → positive；无效交付 → 负。
- **不进**：争议中（未定）、未结算、被 `admin_adjust` 撤销的原事件（撤销以一次反向 `observe` 表示，不重放原事件）。
- **防自放大**：同一事件只 `observe` 一次，幂等键＝事件 id，证据串形如 `bounty:<event_id>:<difficulty>:<delta>`（audit 内存证截断 200 字符）。
- 负证据照常下调，**不因历史高分豁免**（对齐 links.py 的「反例击穿」），故映射不得只推 positive。

### 4.4 量纲桥接

公开声誉是**累积整数**（无上界、不衰减），内部信任是 **[0, cap] 概率**。不做线性映射：线性会把无界累积量一律截断到 cap——高分者做再多也停在 cap，失去分辨率；且「累计做了多少」与「下一次是否可信」不是同一件事。桥接取**逐次事件折算**而非总分折算：每个合格事件触发一次 `observe`，方向由 `delta` 符号决定，强度不叠加（多次事件＝多次 ±步长，天然受 cap 与衰减约束）。性质：**单调**（`delta>0` 只推高、`delta<0` 只推低）、**有界**（clamp 到 `[0, p_trust_cap]`）、**可复算**（给定事件序列，用步长／衰减／cap 可重放）。注意后一条只在内部面成立：步长与 cap 属本机私有标定，故内部信任不可对外复算，也就不得对外披露。

### 4.5 诚实边界

两套信任**不一致是正常的**：对内有衰减（30 天无观测向初值回归）、有 cap，对外不衰减、无上界；「站内 100 分」不等价于「p_trust 高」。**不得互相覆盖**：不得用公开声誉覆盖 `p_trust`，也不得用 `p_trust` 改写事件表；唯一合法耦合点是 `observe` 这一证据入口。数值结论一律降级为「结构成立、权重待标」——`UP_STEP`／`DOWN_STEP`／`DECAY_DAYS` 未取证到标定值。

## 五、边界与待裁

### 5.1 事实边界

| 项 | 状态 |
|---|---|
| 质量系数 Q 的档位值（1.0/0.8/0.6/0.4） | **建议值待裁**（结构来自 `tasks_submission.round`，数值未经回放标定） |
| 加式的**基准质量 0.5** | **建议值待裁**；取 0.5 的用意是让「返工到上限仍全过」≈ v1.0 原分，避免对存量账本系统性下移 |
| 协作分 C 是否折算进 `delta` | **待裁**（本设计建议**先不进**，只作独立协作榜，保持 v1.0 阈值标定不变） |
| 负向指标上限（单任务负向总额 ≤ base） | **建议值**，与 v1.0「无效交付 −base」同级 |
| 站内验证明细是否足够细 | **未取证**（`tasks_submission` 的 `review_comment` 是否为结构化逐条判定，影响 E 的可复算性） |
| 两个合成口径对**存量账本**的迁移影响 | **未回放实算**（撰写单元如实标注） |
| 内部信任桥接的强度参数 | `UP_STEP=0.05`／`DOWN_STEP=0.20`／`DECAY_DAYS=30` 均为**未标定占位值**（`md_cg/links.py` docstring 自述）⇒ 桥接「结构成立、权重待标」 |

### 5.2 待使用者裁定

1. **是否按本设计修订 v1.0 计分章节**（Q／E／加式／协作分是否入稿）。
2. **质量是否单独出榜**（加式下返工只少加分不扣分，高质量激励偏弱；缓解办法是质量单列榜并公示）。
3. **协作分 C 的口径**（计不计分、单月上限、防刷判据是否照 §二·2.6）。
4. **公开面披露粒度**：事件表逐条公开到什么程度（含不含 `review_comment` 原文）。
5. **对内信任桥接是否开工**（§四的 `observe` 通道；涉及内部 `links.py` 一侧的写入权限与幂等键落点）。

### 5.3 本设计的自我边界

- **设计稿**：不变量、系数、桥接形式都是**结构与判据**，不是实现；所有数值待标定。
- **未做对抗性验证**：未构造"故意破坏"证明这些判据在真实攻击（串通互评、批量刷单、跨账号对偶）下有效。
- **单站视角**：只覆盖悬赏站自身的贡献评价；外部贡献者的**代码质量**不在本设计的可核范围内（受 §一·1.3 边界所限）。
